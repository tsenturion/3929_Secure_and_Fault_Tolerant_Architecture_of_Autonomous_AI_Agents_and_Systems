# Практическое задание №5. Разработка системы мониторинга, аудита и обнаружения аномалий автономных ИИ-агентов

**Модуль 5. Мониторинг, аудит и обнаружение аномалий**

## Цель

Разработать систему мониторинга и аудита автономных ИИ-агентов, обеспечивающую отслеживание их действий, проверку целостности истории операций, измерение эффективности работы и обнаружение потенциально опасного поведения.

Реализовать **tamper-evident аудит на основе хеш-цепочки**, централизованное логирование и трассировку взаимодействий между агентами, расчёт ключевых показателей эффективности (success rate, tool call frequency), а также систему обнаружения аномалий и злоупотреблений.

В ходе выполнения необходимо освоить методы обеспечения наблюдаемости агентных систем, научиться выявлять несанкционированные изменения журналов, анализировать последовательности действий агентов и автоматически обнаруживать признаки неисправностей или потенциальных атак.

## Задание (шаги)

### Шаг 1. Подготовка проекта и архитектуры мониторинга

Продолжить разработку системы обработки ИТ-инцидентов интернет-магазина из предыдущих практических заданий.

Создать каталог `assignments/05/` и реализовать отдельный компонент `ObservabilityService`, отвечающий за аудит, логирование, сбор метрик и обнаружение аномалий.

Предусмотреть четыре подсистемы:

| Подсистема         | Назначение                                             |
| ------------------ | ------------------------------------------------------ |
| `AuditLogger`      | Сохранение событий и проверка целостности истории      |
| `TraceManager`     | Связывание действий агентов и сервисов в единые трассы |
| `MetricsCollector` | Расчёт показателей эффективности                       |
| `AnomalyDetector`  | Выявление подозрительных последовательностей действий  |

В качестве основного сценария использовать обращение `REQ-1842` о массовой задержке электронных уведомлений.

Система должна отслеживать полный жизненный цикл обращения:

1. Получение обращения агентом диагностики.
2. Вызов инструментов мониторинга и чтения регламентов.
3. Выполнение проверок безопасности.
4. Формирование рекомендации.
5. Сохранение черновика инцидента.
6. Подтверждение или отклонение рекомендации дежурным.
7. Регистрация инцидента либо передача на ручной разбор.

Каждая значимая операция должна оставлять запись, по которой можно установить инициатора, время выполнения, результат и связь с другими событиями.

### Шаг 2. Реализация защищённого журнала аудита

Создать класс `AuditLogger`, сохраняющий события в SQLite.

Каждая запись должна содержать следующие поля:

| Поле            | Назначение                                          |
| --------------- | --------------------------------------------------- |
| `event_id`      | Уникальный последовательный номер события в цепочке |
| `timestamp`     | Время события в UTC                                 |
| `case_id`       | Идентификатор обращения                             |
| `run_id`        | Идентификатор прогона агента                        |
| `actor`         | Идентичность инициатора                             |
| `action`        | Выполненное или запрошенное действие                |
| `decision`      | Решение политики или исполнителя                    |
| `result`        | Результат операции                                  |
| `previous_hash` | Хеш предыдущей записи                               |
| `current_hash`  | Хеш текущей записи                                  |

Для формирования хешей использовать алгоритм **BLAKE2b** из стандартной библиотеки Python.

Организовать отдельную цепочку событий для каждого обращения и каждого дня UTC.

Хеш текущей записи должен зависеть от её номера, содержимого и хеша предыдущей записи.

Реализовать функции:

- `append_event()` — добавление события;
- `calculate_hash()` — вычисление хеша;
- `verify_chain()` — проверка последовательности;
- `get_audit_history()` — получение истории обращения.

Для вычисления хеша использовать стабильную сериализацию данных. Порядок ключей и формат представления значений не должны изменять результат при повторной проверке того же события.

После добавления события запрещается незаметно изменять предыдущие записи.

### Шаг 3. Проверка целостности хеш-цепочки

Создать функцию `verify_chain()`, проверяющую целостность сохранённой последовательности.

Необходимо проверять:

1. Последовательность номеров событий.
2. Соответствие `previous_hash` хешу предыдущей записи.
3. Совпадение сохранённого `current_hash` с повторно вычисленным.
4. Отсутствие пропущенных записей.
5. Соответствие последней подтверждённой записи доверенной контрольной точке.

Подготовить три копии учебного журнала.

**Сценарий А. Исходная последовательность**

Журнал содержит корректные записи диагностики и подтверждения инцидента P2.

Ожидаемый результат: целостность подтверждена.

**Сценарий Б. Изменение записи**

В одной из сохранённых записей изменить время подтверждения инцидента, не пересчитывая хеши.

Ожидаемый результат: `event_modified` с указанием номера первой повреждённой записи.

**Сценарий В. Удаление последних событий**

Удалить несколько последних записей журнала.

Ожидаемый результат: `truncated` с указанием номера первой отсутствующей записи при сравнении с ранее сохранённой контрольной точкой.

Проверить, что после изменения содержимого хотя бы одного события повторная проверка цепочки обнаруживает несоответствие.

### Шаг 4. Реализация независимой службы контрольных точек

Добавить отдельный компонент `AuditWitness`, подтверждающий состояние журнала аудита.

Служба должна периодически получать сведения о последней записи цепочки и сохранять:

- идентификатор обращения;
- дату цепочки в UTC;
- номер последнего подтверждённого события;
- хеш последнего подтверждённого события;
- время формирования контрольной точки.

Установить интервал проверки — 5 секунд.

Организовать хранение контрольных точек отдельно от основного журнала аудита.

При использовании Docker:

- Исполнитель должен записывать события в своё хранилище.
- `AuditWitness` должен получать доступ к данным журнала только для чтения.
- Контрольные точки должны сохраняться в отдельном томе.
- Исполнитель не должен иметь права изменять контрольные точки.
- Контейнер свидетеля аудита должен работать без сетевого доступа.

Предусмотреть хранение записей за текущий день UTC и 29 предыдущих дней.

Проверить, что изменение или удаление ранее подтверждённых событий обнаруживается при сравнении журнала с контрольной точкой.

Если после последней контрольной точки появились новые события, они должны получать статус ожидания подтверждения. Их связность необходимо проверять отдельно.

**Важно:** хеш-цепочка позволяет обнаруживать изменения, но не предотвращает их физически. Для обнаружения удаления конца журнала требуется независимая доверенная контрольная точка.

### Шаг 5. Реализация структурированного логирования

Создать подсистему `StructuredLogger`, сохраняющую диагностические события в формате JSON Lines.

Каждая строка файла должна представлять отдельный JSON-объект.

Обязательные поля:

- `timestamp` — время события;
- `level` — уровень логирования;
- `service` — название сервиса;
- `case_id` — идентификатор обращения;
- `run_id` — идентификатор прогона;
- `trace_id` — идентификатор распределённой трассы;
- `operation` — выполняемая операция;
- `duration_ms` — продолжительность;
- `result_code` — код результата.

Пример структуры события:

```json
{
  "timestamp": "2026-11-16T14:12:05Z",
  "level": "INFO",
  "service": "diagnostic-agent",
  "case_id": "REQ-1842",
  "run_id": "run-001",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "operation": "get_service_status",
  "duration_ms": 125,
  "result_code": "allowed"
}
```

Реализовать сохранение журналов в каталог `/app/logs` соответствующего контейнера.

Предусмотреть уровни `DEBUG`, `INFO`, `WARNING` и `ERROR`.

Необходимо обеспечить:

1. Корректную сериализацию событий.
2. Фиксацию ошибок выполнения инструментов.
3. Запись результатов проверок безопасности.
4. Отсутствие API-ключей, JWT, паролей и контактов покупателей в логах.
5. Возможность поиска событий по `run_id` и `trace_id`.

### Шаг 8. Расчёт ключевых метрик эффективности

Создать компонент `MetricsCollector`, рассчитывающий показатели на основе сохранённых прогонов и событий аудита.

Реализовать следующие метрики.

**1. Success Rate — доля успешных обращений**

Рассчитывать отношение количества успешно закрытых обращений к общему количеству закрытых обращений за выбранный период.

В успешные закрытия включать завершения агентом и успешные ручные закрытия.

Для каждого обращения учитывать только первый зафиксированный итог закрытия.

**2. Agent Success Rate — доля завершений агентным маршрутом**

Рассчитывать отношение количества обращений, успешно завершённых агентным маршрутом, к общему количеству закрытых обращений.

Успешное завершение после согласования оператором относится к агентному маршруту.

**3. Tool Call Frequency — частота вызовов инструментов**

Рассчитывать количество зарегистрированных попыток вызова инструмента за выбранный временной интервал.

Предусмотреть окна 5, 15 и 60 минут.

**4. Tool Failure Rate — доля неуспешных вызовов**

Рассчитывать отношение количества вызовов, завершившихся ошибкой или отказом, к общему числу попыток вызова инструментов.

**5. Average Execution Time — среднее время выполнения**

Рассчитывать среднюю продолжительность автоматических диагностических прогонов отдельно от ожидания подтверждения оператором.

Для вычислений использовать данные SQLite.

### Шаг 10. Реализация обнаружения аномалий и злоупотреблений

Создать класс `AnomalyDetector`, анализирующий журнал аудита и выявляющий подозрительные последовательности событий.

Реализовать три обязательных правила.

**Правило 1. Всплеск вызовов инструментов**

Аномалия обнаруживается при одновременном выполнении условий:

- За последние 60 секунд зарегистрировано не менее 6 попыток вызова одного инструмента одним сервисом.
- Частота за это окно как минимум вдвое превышает среднюю частоту за предшествующие 5 минут.

Подсчёт должен выполняться по одному обращению.

Необходимо учитывать успешные и отклонённые вызовы.

**Правило 2. Серия отказов при регистрации**

Аномалия обнаруживается, если в течение 60 секунд одному сервису отказано не менее трёх раз при получении разрешения на согласование или попытке зарегистрировать инцидент.

**Правило 3. Приближение к лимиту прогона**

Аномалия обнаруживается, если:

- У незавершённого прогона за последние 5 минут осталось не более одного допустимого действия или шага.
- Либо исполнитель отклонил вызов с кодом `action_limit_reached`.

Для каждой аномалии формировать объект со следующими полями:

- `alert_id`;
- `rule_id`;
- `case_id`;
- `service`;
- `severity`;
- `detected_at`;
- `description`;
- `related_event_ids`;
- `run_ids`.

Предусмотреть уровни серьёзности `LOW`, `MEDIUM` и `HIGH`.

### Шаг 11. Разработка тестовых сценариев аномального поведения

Для обращения `REQ-1842` подготовить отдельную учебную выборку событий.

Смоделировать:

1. Десять попыток вызова `get_service_status` за одну минуту.
2. Шесть успешных чтений одной версии снимка мониторинга в разных допустимых прогонах.
3. Несколько отклонённых повторных чтений с кодом `action_limit_reached`.
4. Три отказа при регистрации из-за отсутствия назначения дежурного.
5. Приближение одного диагностического прогона к установленному лимиту действий.

Для проверки всплеска дополнительно подготовить спокойный базовый интервал, в котором частота чтений значительно ниже.

Проверить, что система обнаруживает все три типа аномалий и не формирует ложное оповещение, если количество вызовов или частота не достигают установленных порогов.

Для каждого оповещения обеспечить возможность получить связанные записи аудита.

Дополнительно реализовать подсчёт одинаковых снимков мониторинга. Для этого сохранять отпечаток содержимого успешно полученного снимка, не включая в него секреты или персональные сведения.

Одинаковые отпечатки должны позволять установить, сколько раз агенты получали одну и ту же версию данных.

### 2. Вычисление криптографических хешей

Для реализации BLAKE2b использовать стандартную библиотеку `hashlib`.

```python
import hashlib
```

При формировании хеша учитывать содержимое события, его номер и предыдущий хеш.

Для корректной работы необходимо заранее определить формат сериализации и использовать его во всех проверках.

### 3. Работа с временными метками

Для хранения времени использовать `datetime` с часовым поясом UTC.

Не следует смешивать локальное время сервера, время контейнера и время, переданное агентом.

При расчёте частоты событий проверять, что сравниваются временные метки из одной системы отсчёта.

### 4. Структурированное логирование

Для записи событий использовать модуль `logging` с JSON-форматированием.

Каждая запись должна представлять самостоятельный JSON-объект.

Не рекомендуется записывать диагностическую информацию исключительно обычным `print()`, поскольку такие сообщения сложнее связывать с конкретными прогонами и обрабатывать автоматически.

### 5. Распределённая трассировка

Для генерации идентификаторов использовать `uuid` или криптографически безопасные генераторы.

Передавать `trace_id` между компонентами через контекст запроса.

При создании дочерней операции сохранять связь с родительской, чтобы можно было восстановить полную последовательность выполнения.

### 6. Расчёт метрик

Для хранения результатов можно использовать SQLite и SQL-запросы с агрегатными функциями.

При расчёте Success Rate не следует считать каждый повторный прогон отдельным закрытым обращением.

Частоту вызовов необходимо рассчитывать по фактическому числу попыток в заданном временном окне, включая отказы исполнителя.

### 7. Поиск аномалий

Для анализа частоты вызовов удобно группировать события по `case_id`, `service` и `action`.

Необходимо отдельно рассчитывать количество событий в текущем окне и базовую частоту предыдущего периода.

Случай отсутствия событий в базовом периоде требует отдельной обработки без деления на ноль.

### 8. Безопасность мониторинга

Система наблюдаемости сама является компонентом, требующим защиты.

Не следует предоставлять обычному агенту право изменять события аудита, контрольные точки или результаты проверок целостности.

При выводе диагностических данных исключать секреты, токены и персональные сведения.

## Советы по улучшению работы

**1. Независимость системы аудита.** Разместить службу проверки целостности отдельно от исполнителя. Это уменьшит вероятность того, что компрометация одного компонента позволит незаметно изменить журнал и контрольные точки.

**2. Защита от подмены истории.** Сохранять контрольные точки в независимом хранилище с ограниченными правами записи. Хеш-цепочка без внешнего доверенного подтверждения не гарантирует обнаружение полностью переписанной истории.

**3. Повышение качества трассировки.** Использовать единые соглашения об именовании операций и передаче идентификаторов. Это упростит поиск причин ошибок и измерение времени отдельных этапов.

**4. Оптимизация хранения журналов.** Настроить ротацию файлов, ограничения размера и сроки хранения. Не создавать отдельные индексируемые метки Loki для каждого уникального `trace_id`.

**5. Снижение ложных срабатываний.** Анализировать не только абсолютное количество вызовов, но и изменение частоты относительно базового периода. Различать обычную повышенную нагрузку и подозрительные повторные обращения.

**6. Расширение системы метрик.** Дополнительно рассчитывать среднее количество инструментальных вызовов на обращение, долю ручных разборов и частоту отказов по отдельным политикам безопасности.

**7. Контроль самого мониторинга.** Предусмотреть сигнал о прекращении поступления журналов, недоступности Loki или длительном отсутствии новых контрольных точек аудита.
