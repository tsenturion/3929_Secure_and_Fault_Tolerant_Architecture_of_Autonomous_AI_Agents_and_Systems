# Практическое задание №4. Разработка изолированной архитектуры автономных ИИ-агентов с защищённой аутентификацией и авторизацией

**Модуль 4. Изоляция и управление доступом (IAM)**

## Цель

Разработать защищённую инфраструктуру для автономных ИИ-агентов, реализующую принципы изоляции процессов, минимальных привилегий, криптографической идентификации и контроля доступа между компонентами системы.

Реализовать контейнеризацию агентных сервисов, аутентификацию с использованием эфемерных токенов, проверку сертификатов и подтверждение владения ключом TPM, межагентную аутентификацию через mTLS и OAuth 2.0, а также механизм отложенной авторизации с одноразовыми transaction tokens.

В ходе выполнения необходимо закрепить понимание различий между аутентификацией и авторизацией, освоить безопасное взаимодействие распределённых компонентов и обеспечить невозможность выполнения критических операций без действительных полномочий и подтверждения.

## Задание (шаги)

### Шаг 1. Подготовка многоагентной архитектуры

Продолжить разработку системы обработки ИТ-инцидентов из предыдущих практических заданий.

Создать каталог `assignments/04/` и подготовить архитектуру, состоящую из следующих компонентов:

| Компонент          | Назначение                                            |
| ------------------ | ----------------------------------------------------- |
| `diagnostic-agent` | Анализ ИТ-обращений и выбор диагностических действий  |
| `runbook-agent`    | Получение опубликованных регламентов                  |
| `executor`         | Проверка полномочий и выполнение разрешённых операций |
| `monitoring`       | Предоставление данных о состоянии сервисов            |
| `model-gateway`    | Изолированный доступ к внешним языковым моделям       |
| `keycloak`         | Выпуск и проверка сервисных учётных данных            |
| `storage`          | Хранение прогонов, подтверждений и инцидентов         |

В качестве основного сценария использовать обращение `REQ-1842` о массовой задержке электронных уведомлений.

Необходимо обеспечить следующий порядок обработки:

1. Агент диагностики получает обращение.
2. Агент определяет необходимые диагностические действия.
3. Исполнитель проверяет полномочия агента и допустимость каждого действия.
4. Для поиска регламента используется отдельный `runbook-agent`.
5. Результаты диагностики используются для формирования рекомендации P2.
6. Дежурный оператор подтверждает создание инцидента.
7. Исполнитель проверяет подтверждение и выполняет регистрацию.

Каждый компонент должен иметь собственные полномочия. Успешная аутентификация одного агента не должна автоматически предоставлять ему права другого.

### Шаг 2. Контейнеризация сервисов с использованием Docker

Подготовить `Dockerfile` для Python-сервисов и файл `compose.yaml` для запуска компонентов системы.

Настроить контейнеры с учётом принципа минимальных привилегий.

Обязательные требования:

1. Запускать серверные Python-процессы от непривилегированного пользователя с UID `10001`.
2. Запретить повышение привилегий через `no-new-privileges`.
3. Удалить дополнительные Linux capabilities с помощью `cap_drop: [ALL]`.
4. Использовать корневую файловую систему в режиме только для чтения.
5. Ограничить количество процессов в контейнерах.
6. Использовать стандартный профиль seccomp Docker.
7. Организовать временное хранилище через ограниченный `tmpfs`.
8. Хранить состояние трекера и журналы в отдельных томах.
9. Исключить монтирование Docker socket и лишних каталогов хостовой системы.

Для временных файлов предусмотреть каталог `/tmp`, доступный на запись.

Постоянное состояние исполнителя должно храниться отдельно от файловой системы контейнера и сохраняться после его пересоздания.

Настроить сети Docker Compose так, чтобы диагностический агент, исполнитель, мониторинг и шлюз моделей имели только необходимую сетевую связность.

**Важно:** контейнер агента не должен иметь прямого доступа к базе данных исполнителя и секретам облачных моделей.

### Шаг 3. Проверка изоляции контейнеров

Скрипт должен:

- Проверять сведения о capabilities и seccomp из `/proc/self/status`.
- Проверять невозможность записи в корневую файловую систему.
- Проверять наличие разрешённого тома для состояния.
- Проверять отсутствие Docker socket.

- Проверять невозможность создания нового пространства имён монтирования без необходимых привилегий.

Результаты представить в виде отчёта с названиями проверок и статусами `PASS` или `FAIL`.

Отдельно проверить, что исполнитель сохраняет возможность чтения и записи в свой разрешённый том состояния.

Использовать для тестирования только собственные учебные контейнеры. Скрипт не должен пытаться модифицировать конфигурацию хостовой операционной системы.

### Шаг 4. Реализация эфемерных токенов аутентификации

Настроить Keycloak как локальный сервер идентификации для выдачи краткоживущих сервисных токенов.

Использовать OAuth 2.0 с потоком `client_credentials`.

Создать клиент `diagnostic-agent`, которому разрешено получать токен для обращения к исполнителю.

Установить срок действия access token — **20 секунд**.

Реализовать функцию `get_access_token()`, запрашивающую токен у Keycloak.

На стороне Executor реализовать проверку JWT:

| Параметр         | Проверяемое значение       |
| ---------------- | -------------------------- |
| Алгоритм подписи | RS256                      |
| `iss`            | Доверенный issuer Keycloak |
| `aud`            | `incident-executor`        |
| `azp`            | `diagnostic-agent`         |
| `scope`          | `executor.access`          |
| `exp`            | Токен не просрочен         |
| `iat`            | Время выдачи корректно     |

Подпись необходимо проверять по открытым ключам доверенного Keycloak, а не только декодировать содержимое JWT.

В режиме эфемерных токенов передавать сервисный токен в `X-Service-Token`. Учётные данные оператора передавать отдельно.

Создать проверочные сценарии:

1. Корректный токен — доступ разрешён.
2. Токен с получателем `monitoring-api` — отказ `service_audience_invalid`.
3. Просроченный токен — отказ `service_token_expired`.
4. Токен с изменённой подписью — отказ.
5. Токен без необходимого `scope` — отказ.

### Шаг 5. Автоматическое обновление токенов

Добавить компонент `TokenManager`, управляющий жизненным циклом сервисных токенов.

Реализовать:

- Хранение текущего токена в памяти процесса.
- Проверку оставшегося срока действия.
- Обновление токена перед истечением срока.
- Повторный запрос при отказе из-за просроченного токена.
- Ограничение количества повторов.

Если Executor возвращает `401 service_token_expired` до выполнения инструмента, агент должен получить новый токен и повторить исходный запрос не более одного раза.

При повторе исполнитель обязан заново проверить все полномочия, ресурс и допустимость инструмента.

Необходимо исключить бесконечные попытки обновления токена при недоступности Keycloak.

Если получить новый токен невозможно, операция должна завершиться отказом без выполнения действия.

В журнале разрешается сохранять время обновления и код ошибки, но не значение самого токена.

### Шаг 6. Идентификация агентов с помощью X.509-сертификатов

Создать учебный центр сертификации (CA) и организовать выпуск отдельных сертификатов для агента диагностики и исполнителя.

Для сертификата агента использовать URI SAN:

`urn:dispatcher:service:diagnostic-agent`

Для серверного сертификата исполнителя использовать DNS-имя `executor`.

Реализовать проверку:

1. Подписи сертификата доверенным центром сертификации.
2. Срока действия сертификата.
3. Допустимости его назначения для клиентской или серверной аутентификации.
4. Соответствия DNS-имени сервера.
5. Соответствия URI SAN ожидаемой сервисной роли.

Настроить TLS-вход исполнителя таким образом, чтобы запросы без корректного клиентского сертификата отклонялись.

Для проверки подготовить четыре сценария:

| Сценарий                           | Ожидаемый результат      |
| ---------------------------------- | ------------------------ |
| Корректный сертификат агента       | Доступ разрешён          |
| Сертификат отсутствует             | `certificate_required`   |
| Сертификат подписан неизвестным CA | TLS-соединение отклонено |
| URI SAN не соответствует роли      | Доступ запрещён          |

Предусмотреть механизм плановой ротации сертификата агента.

После выпуска нового сертификата повторить проверку идентичности и убедиться, что новый серийный номер принимается системой при неизменной сервисной роли.

Закрытый ключ учебного CA не должен передаваться в контейнеры агентов или исполнителя.

### Шаг 7. Подтверждение владения ключом TPM

Добавить механизм подтверждения идентичности агента с использованием программного TPM.

Для учебного стенда использовать эмулятор `swtpm` и инструменты `tpm2-tools`.

Подготовить отдельный RSA-ключ в эмуляторе TPM.

Исполнитель должен хранить доверенный открытый ключ и проверять подписи, сформированные соответствующим закрытым ключом.

Реализовать протокол challenge-response:

1. Агент запрашивает проверку владения ключом.
2. Исполнитель генерирует случайный одноразовый `nonce`.
3. Система связывает `nonce` с идентификатором сервиса, оператором и серийным номером сертификата.
4. Срок действия запроса устанавливается на 30 секунд.
5. Агент подписывает подготовленное сообщение с помощью TPM.
6. Исполнитель проверяет подпись зарегистрированным открытым ключом.
7. После первой попытки проверки запрос становится недействительным.

Подготовить тесты:

- Корректная подпись — проверка успешна.
- Изменённая подпись — отказ.
- Повторное использование запроса — `challenge_inactive`.
- Подпись после истечения 30 секунд — отказ.
- Использование запроса другой сервисной идентичностью — отказ.

Учесть, что программный TPM подтверждает владение ключом эмулятора. Он не является доказательством аппаратной подлинности устройства.

### Шаг 8. Межагентная аутентификация через mTLS и OAuth

Настроить защищённое взаимодействие двух агентов:

- `diagnostic-agent` — агент диагностики;
- `runbook-agent` — агент регламентов.

Оба агента должны иметь собственные сертификаты, ключи и учётные записи OAuth.

Настроить mTLS для соединений с исполнителем.

При каждом запросе исполнитель должен:

1. Проверить клиентский сертификат.
2. Определить сервисную идентичность по URI SAN.
3. Проверить подпись и срок действия OAuth-токена.
4. Проверить issuer и audience.
5. Сопоставить `azp` токена с идентичностью сертификата.
6. Проверить область доступа `scope`.
7. Убедиться, что токен привязан к предъявленному сертификату.

Для привязки токена использовать подтверждение владения сертификатом через `cnf.x5t#S256`.

Настроить следующие разрешения:

| Агент            | Разрешённые области                  |
| ---------------- | ------------------------------------ |
| diagnostic-agent | `executor.access`, `incidents.write` |
| runbook-agent    | `runbooks.read`                      |

Наличие `incidents.write` не должно отменять необходимость подтверждения дежурным оператором.

Реализовать три тестовых запроса:

**Сценарий А.** Агент регламентов обращается к исполнителю с корректным сертификатом и токеном для получения `RB-NOTIFY-07`.

Ожидаемый результат: успешное получение опубликованного регламента.

**Сценарий Б.** Агент регламентов пытается зарегистрировать инцидент.

Ожидаемый результат: `service_scope_forbidden`.

**Сценарий В.** Агент передаёт корректный токен без клиентского сертификата.

Ожидаемый результат: TLS-вход отклоняет запрос с `certificate_required`.

Дополнительно проверить попытку использовать токен одного агента вместе с сертификатом другого.

Такой запрос должен отклоняться до обращения к защищённому ресурсу.

### Шаг 9. Реализация отложенной авторизации (Deferred Authorization)

Разработать механизм одноразовых transaction tokens для подтверждения критических операций.

В качестве критической операции использовать регистрацию инцидента по обращению `REQ-1842`.

Разделить процесс на две стадии:

**Стадия 1. Выдача разрешения**

Дежурный оператор просматривает подготовленный черновик и подтверждает его параметры.

Исполнитель проверяет:

- идентичность и полномочия оператора;
- назначение на очередь «Уведомления»;
- допустимость приоритета P2;
- состояние черновика;
- наличие обязательных доказательств;
- срок согласования;
- соответствие подтверждаемой версии сохранённому черновику.

Если проверки успешны, Executor выдаёт одноразовый transaction token.

**Стадия 2. Выполнение операции**

Клиент отправляет transaction token и `Idempotency-Key` для регистрации инцидента.

Исполнитель повторно проверяет действительность разрешения и допустимость операции.

Только после успешного прохождения проверок создаётся запись в трекере.

Для реализации допускается использовать два HTTP-эндпоинта:

- `POST /api/runs/{id}/approval-token` — получение разрешения;
- `POST /api/runs/{id}/resolution` — выполнение согласованной операции.

Токен должен быть криптографически случайным и иметь срок действия не более 30 секунд, не превышающий оставшийся срок согласования черновика.

### Шаг 10. Защита transaction tokens от подмены и повторного использования

Для каждого transaction token сохранять на стороне Executor:

- хеш токена;
- идентификатор прогона;
- идентификатор обращения;
- идентичность сервиса;
- идентичность оператора;
- параметры публикации;
- версию согласованного черновика;
- срок действия;
- статус использования;
- идентификатор согласования.

Контекст разрешения должен храниться в SQLite.

Необходимо обеспечить следующие правила:

1. Токен разрешает выполнение только конкретной согласованной операции.
2. Изменение приоритета или очереди после согласования делает ранее выданное разрешение недействительным.
3. Использование токена другим оператором или сервисом запрещено.
4. Просроченный неиспользованный токен отклоняется.
5. Новая операция с уже использованным токеном запрещена.
6. При успешном выполнении токен погашается.
7. Результат регистрации сохраняется для безопасного повторения запроса после потери ответа.

Использовать транзакцию SQLite для атомарного выполнения регистрации, погашения токена и сохранения результата.

### Шаг 11. Проверка изменения согласованных параметров

Подготовить сценарий для обращения `REQ-1842`.

Исходные параметры:

- Приоритет: P2.
- Очередь: «Уведомления».
- Состояние: `awaiting_approval`.

Порядок проверки:

1. Получить подтверждение оператора.
2. Выдать transaction token.
3. Изменить приоритет черновика с P2 на P1.
4. Попытаться выполнить регистрацию со старым токеном.
5. Проверить отказ `approval_changed`.
6. Восстановить приоритет P2.
7. Получить новое подтверждение и новый токен.
8. Успешно зарегистрировать инцидент.
9. Повторить исходный запрос с тем же `Idempotency-Key`.

Ожидаемые результаты:

| Действие                                         | Результат                        |
| ------------------------------------------------ | -------------------------------- |
| Регистрация после подмены P2 на P1               | `approval_changed`, 0 инцидентов |
| Регистрация с новым разрешением                  | Создан один инцидент             |
| Повтор с тем же токеном и ключом идемпотентности | Возвращён прежний идентификатор  |
| Повтор с изменёнными параметрами                 | Отказ без повторной записи       |
| Попытка использовать токен для другого обращения | Отказ                            |

Для чистого учебного хранилища успешная регистрация должна создавать `INC-3071`.

Проверить, что после потери ответа успешно завершённой операции повтор с тем же токеном и ключом идемпотентности возвращает сохранённый результат после повторной проверки личности и прав.

| 16  | Корректный transaction token                                    | Регистрация разрешена      |
| 17  | Просроченный transaction token                                  | Регистрация запрещена      |
| 18  | Изменение согласованного черновика                              | `approval_changed`         |
| 19  | Повтор успешной регистрации с тем же ключом                     | Прежний идентификатор      |
| 20  | Попытка повторного использования разрешения для другой операции | Отказ                      |

Для проверки времени использовать управляемые часы или подмену функции получения текущего времени.

Криптографические и сетевые проверки проводить как отдельными модульными, так и интеграционными тестами.

### 2. Настройка Docker

Для защиты контейнеров использовать параметры:

```yaml
read_only: true
cap_drop:
  - ALL
security_opt:
  - no-new-privileges:true
pids_limit: 128
```

Дополнительно потребуется настроить непривилегированного пользователя, `tmpfs`, volumes и сети.

Изоляция должна проверяться на практике, поскольку наличие параметров в Compose не гарантирует корректной конфигурации всех компонентов.

### 3. Проверка JWT

Для проверки токенов удобно использовать библиотеку `PyJWT`.

При декодировании обязательно проверять подпись, ожидаемый алгоритм, `issuer`, `audience`, срок действия и необходимые дополнительные поля.

Нельзя принимать алгоритм подписи из недоверенного заголовка токена без ограничения перечня допустимых алгоритмов.

### 4. Работа с сертификатами

Для выпуска и проверки X.509-сертификатов можно использовать библиотеку `cryptography`.

При TLS-подключении следует проверять цепочку доверия и имя сервера.

Права агента рекомендуется связывать с URI SAN, а не только с отображаемым именем сертификата.

### 5. Работа с TPM

Для учебной реализации использовать `swtpm` и `tpm2-tools`.

Случайные значения challenge генерировать с помощью криптографически безопасного генератора.

Каждый challenge должен иметь уникальный идентификатор, срок действия и привязку к проверяемой идентичности.

### 6. Проверка межагентного доступа

mTLS отвечает за проверку сторон TLS-соединения, а OAuth-токен предоставляет сведения о разрешённых областях доступа.

Обе проверки должны выполняться независимо.

Исполнитель не должен доверять строке с именем агента, переданной в обычном поле HTTP-запроса.

### 7. Хранение transaction tokens

Для генерации токенов можно использовать модуль `secrets`.

Сами токены не следует сохранять в журналах или базе данных в открытом виде.

Вместо этого можно хранить криптографический хеш токена, а при получении запроса вычислять и проверять соответствующее значение.

Для записи инцидента и погашения разрешения использовать атомарную транзакцию SQLite.

### 8. Проверка идемпотентности

`Idempotency-Key` должен связывать повторный запрос с уже выполненной операцией.

При повторе необходимо проверять идентичность вызывающего участника и соответствие параметров исходному запросу.

Совпадение одного только ключа идемпотентности не должно разрешать доступ к результатам чужой операции.

## Советы по улучшению работы

**1. Разделение доверенных областей.** Организовать независимые сетевые сегменты для агента, исполнителя, источников данных и шлюза моделей. Минимизировать количество компонентов, имеющих доступ к внешним сетям.

**2. Управление жизненным циклом секретов.** Реализовать плановую замену сертификатов и сервисных ключей. Учитывать срок действия, возможность отзыва и безопасное хранение закрытых ключей.

**3. Усиление Zero Trust.** Проверять сервисную идентичность, OAuth scope, целевой ресурс и операцию при каждом запросе. Не считать внутреннюю сеть Docker достаточным доказательством доверия.

**4. Проверка отказоустойчивости IAM.** Добавить тесты на временную недоступность Keycloak, истечение сертификатов и нарушение связи между сервисами. При невозможности проверить полномочия система должна отклонять защищённые операции.

**5. Безопасность отложенной авторизации.** Не выдавать transaction token до проверки всех необходимых полномочий. Привязывать разрешение к конкретной версии данных и ограничивать время его действия.

**6. Защита конкурентных операций.** Проверить одновременные запросы регистрации одного инцидента. Применять транзакции, ограничения уникальности и идемпотентность.

**7. Раздельное журналирование.** Фиксировать события аутентификации, авторизации, проверки сертификатов и использования transaction tokens, не раскрывая значения токенов и закрытых ключей.
