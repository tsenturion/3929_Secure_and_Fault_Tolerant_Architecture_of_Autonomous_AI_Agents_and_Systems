# Практическое задание №1. Разработка защищённого автономного ИИ-агента для обработки ИТ-инцидентов

**Модуль 1. Введение в автономные ИИ-агенты и угрозы**

## Цель

Разработать программный прототип автономного агента для анализа ИТ-обращений, реализующий жизненный цикл **Observe → Reason → Act**, самостоятельный выбор действий на основании полученных наблюдений, проверку допустимости операций и базовую защиту от угроз.

В ходе выполнения необходимо закрепить понимание различий между автоматизированным сценарием и автономным агентом, изучить практическое применение механизмов безопасности и реализовать отказоустойчивое поведение при возникновении ошибок.

## Задание (шаги)

### Шаг 1. Подготовка проекта и исходных данных

Создать в каталоге `assignments/01/` отдельное Python-приложение для моделирования работы автономного агента.

В качестве основы использовать сценарий учебного проекта **«Безопасный и отказоустойчивый агент для ИТ-заявок»**.

Ситуация: интернет-магазин получает жалобы на задержку электронных писем с подтверждением заказов. Агент должен изучить доступные источники, определить характер проблемы и подготовить рекомендацию дежурному оператору.

Подготовить два тестовых обращения:

| Параметр                     | REQ-1842                      | REQ-1843                       |
| ---------------------------- | ----------------------------- | ------------------------------ |
| Характер проблемы            | Массовая задержка уведомлений | Проблема с отдельной доставкой |
| Возраст старейшего сообщения | 17 минут                      | 2 минуты                       |
| Состояние оплаты             | Работает                      | Работает                       |
| Подходящий регламент         | RB-NOTIFY-07                  | RB-NOTIFY-03                   |
| Ожидаемый результат          | Рекомендация P2               | Проверка отдельного заказа     |

Для `REQ-1842` дополнительно предусмотреть 18 обращений за 10 минут, 4 800 сообщений в очереди и запись об обновлении обработчика в 13:52.

Данные должны храниться в словарях Python или JSON-файлах. Для каждого источника необходимо предусмотреть информацию о его типе и происхождении.

### Шаг 2. Реализация жизненного цикла агента

Реализовать три основных этапа работы:

1. **Observe (наблюдение).** Получение информации об обращении, состоянии очереди уведомлений, журнале развёртываний и доступных регламентах.
2. **Reason (принятие решения).** Анализ накопленных наблюдений и определение следующего необходимого действия.
3. **Act (действие).** Выполнение разрешённой операции чтения, сохранение результата и переход к следующему этапу.

Создать функции `observe()`, `reason()`, `act()` и `run_agent()`.

Агент должен самостоятельно определять последовательность чтения источников. Например, после получения показателей мониторинга он может решить, какой именно регламент необходимо прочитать.

Предусмотреть следующие действия:

- `get_service_status` — получение состояния сервиса;
- `get_deployment_log` — получение сведений о развёртываниях;
- `find_incident_runbook` — поиск регламента массовой задержки;
- `find_individual_runbook` — поиск регламента индивидуальной доставки;
- `finish` — завершение диагностики и формирование результата.

Дополнительно реализовать функцию `run_fixed_route()`, выполняющую заранее установленный перечень чтений без изменения последовательности.

Сравнить работу фиксированного маршрута и агента на двух подготовленных обращениях.

**Важно:** использование реальной языковой модели необязательно. Источник решений допускается имитировать программной логикой, которая выбирает действия на основе текущего состояния. При этом решение не должно определяться исключительно идентификатором обращения.

### Шаг 3. Разработка механизма принятия решений

Реализовать логику, учитывающую результаты мониторинга и сведения из регламентов.

Основные условия:

- Если возраст старейшего сообщения превышает 15 минут, а оформление заказов и оплата работают штатно, агент должен изучить журнал развёртываний и опубликованный регламент `RB-NOTIFY-07`.
- После получения необходимых доказательств агент формирует рекомендацию открыть инцидент P2 в очереди «Уведомления».
- Если возраст старейшего сообщения не превышает 5 минут, агент выбирает регламент `RB-NOTIFY-03` и рекомендует проверить доставку отдельного заказа.
- При недостаточных либо противоречивых сведениях агент не должен самостоятельно назначать приоритет P2. Необходимо предусмотреть передачу обращения на ручной разбор.

Ограничить диагностический прогон пятью действиями. Не допускать бесконечного повторения одного и того же запроса.

Результат работы агента должен содержать идентификатор обращения, собранные наблюдения, выбранный регламент, рекомендацию и итоговый статус.

### Шаг 4. Реализация защиты от основных угроз

Добавить четыре тестовых сценария атак и реализовать соответствующие защитные механизмы.

**1. Prompt injection — внедрение вредоносных инструкций**

Смоделировать ситуацию, при которой агент получает неопубликованную копию `RB-NOTIFY-07`. В тексте копии содержится инструкция зарегистрировать инцидент без согласования с оператором.

Необходимо:

- Проверять статус публикации и происхождение регламента.
- Исключать неподтверждённую копию из источников, используемых для принятия решения.
- Продолжать обработку на основе опубликованного регламента.

**2. Memory poisoning — отравление памяти**

Добавить историческую заметку из ранее закрытого обращения, содержащую ошибочную рекомендацию установить приоритет P3.

Необходимо:

- Отличать исторические сведения от действующих регламентов.
- Не использовать старую рекомендацию как обязательное правило.
- Формировать итог на основании актуальных наблюдений и опубликованного регламента.

**3. Tool misuse — неправильное использование инструментов**

Смоделировать предложение выполнить действие `resend_notifications`, запускающее повторную отправку уведомлений.

Необходимо:

- Реализовать список разрешённых инструментов.
- Проверять выбранное действие до его выполнения.
- Отклонять отсутствующие в списке инструменты.
- Переводить обращение в статус `needs_review` при попытке запрещённого действия.

Запрещённое действие не должно вызываться даже в тестовом режиме.

**4. Data exfiltration — утечка данных**

Добавить в тестовое обращение поле `customer_email`, содержащее вымышленный адрес `buyer-1842@example.invalid`.

Необходимо:

- Отделить служебные сведения от данных, необходимых для диагностики.
- Создать функцию формирования безопасного контекста агента.
- Исключить контакт покупателя из контекста для модели, журнала решений и итогового отчёта.

Проверить отсутствие исходного адреса во всех перечисленных результатах.

### Шаг 5. Реализация согласования действий

Разработать простой механизм подтверждения регистрации инцидента.

После подготовки рекомендации P2 агент должен перейти в состояние `awaiting_approval`.

Предусмотреть два типа пользователей:

- `duty_operator` — дежурный оператор, которому разрешено подтверждать регистрацию;
- `observer` — наблюдатель с доступом только к просмотру результатов.

До подтверждения инцидент не должен появляться в условном трекере.

После подтверждения необходимо создать запись об инциденте с уникальным идентификатором.

Повторное подтверждение того же прогона не должно приводить к созданию дополнительной записи.

Для хранения инцидентов допускается использовать словарь Python или отдельный JSON-файл.

### Шаг 6. Обработка сбоев и журналирование

Реализовать обработку двух ситуаций:

**Сбой источника решений.** После успешного чтения мониторинга источник решений становится недоступен. Агент должен сохранить полученные наблюдения, зафиксировать ошибку и завершить автоматическую диагностику со статусом `needs_review`.

**Потеря ответа после регистрации.** Инцидент успешно записан, но вызывающая программа получает имитацию таймаута. При повторном запросе подтверждения должен возвращаться идентификатор уже созданного инцидента.

Добавить журнал выполнения, содержащий:

- Номер и этап шага: `observe`, `reason`, `act`.
- Выбранное действие и причину выбора.
- Источник полученных данных.
- Результат проверки безопасности.
- Возникшие ошибки.
- Итоговый статус выполнения.

Журнал не должен содержать персональные или другие исключённые из безопасного контекста данные.

### Шаг 7. Тестирование программы

Создать автоматические тесты с использованием `pytest`.

Проверить следующие случаи:

| №   | Проверяемый сценарий             | Ожидаемый результат                              |

| 1   | Массовая задержка REQ-1842       | Рекомендация P2, ожидание согласования           |
| 2   | Индивидуальная проблема REQ-1843 | Рекомендация проверить отдельный заказ           |
| 3   | Prompt injection                 | Неопубликованный регламент не влияет на решение  |
| 4   | Memory poisoning                 | Историческая заметка не изменяет приоритет на P3 |
| 5   | Tool misuse                      | Запрещённая операция отклонена до выполнения     |
| 6   | Data exfiltration                | Контакт отсутствует в контексте и результатах    |
| 7   | Недоступность источника решений  | Переход в `needs_review`, наблюдения сохранены   |

Зафиксировать результаты тестирования и устранить обнаруженные ошибки.

## Подсказки по ключевым частям

### 1. Организация структуры проекта

Рекомендуемая структура:

```text
assignments/
└── 01/
    ├── agent.py
    ├── tools.py
    ├── security.py
    ├── scenarios.py
    ├── test_agent.py
    └── README.md
```

В `agent.py` разместить управление жизненным циклом и принятие решений. В `tools.py` — имитацию инструментов получения данных. В `security.py` — проверки источников, действий и безопасного контекста.

### 2. Выбор инструментов

Для хранения разрешённых операций удобно использовать множество:

```python
ALLOWED_ACTIONS = {
    "get_service_status",
    "get_deployment_log",
    "find_incident_runbook",
    "find_individual_runbook",
    "finish",
}
```

Проверку принадлежности выбранного действия множеству необходимо выполнять до обращения к инструменту.

### 3. Хранение состояния

Использовать отдельный объект или словарь состояния агента. В нём могут находиться:

- идентификатор прогона;
- текущие наблюдения;
- уже выполненные действия;
- доступные источники;
- журнал событий;
- итоговый статус.

На каждом новом шаге `reason()` должен учитывать накопленное состояние. Это позволит избежать повторных запросов и продемонстрировать адаптивное поведение.

### 4. Работа с источниками информации

Каждое наблюдение полезно описывать не только текстом, но и метаданными.

Например, регламент может содержать поля `id`, `source_kind`, `published` и `content`.

При выборе регламента проверять его статус и тип источника, а не искать только подозрительные слова внутри текста.

### 5. Безопасное формирование контекста

Использовать принцип разрешённого списка полей: явно выбирать сведения, которые необходимы агенту для принятия решения.

Не передавать исходный словарь обращения целиком. Наличие дополнительного поля в исходных данных не должно автоматически приводить к его появлению в контексте.

### 6. Обработка исключений

При моделировании сбоев использовать `try` / `except` и собственные исключения там, где это упрощает код.

Обработка ошибки должна изменять статус прогона и сохранять уже полученные наблюдения. Исключение не должно приводить к незаметному продолжению потенциально небезопасного действия.

## Советы по улучшению работы

**1. Разделение ответственности.** Отделить механизм принятия решений от выполнения инструментов. Это упростит проверку действий и позволит в дальнейшем подключать настоящие языковые модели без изменения основных правил безопасности.

**2. Расширение журнала событий.** Добавить временные метки и идентификаторы прогонов. Это позволит восстановить последовательность действий агента и выяснить причину завершения обработки.

**3. Упрощение добавления инструментов.** Вместо длинных конструкций `if` / `elif` использовать словарь, сопоставляющий разрешённые названия инструментов с соответствующими функциями.

**4. Дополнительные проверки.** Предусмотреть обработку пустых результатов, отсутствующих полей, некорректных значений и повторяющихся наблюдений.

**5. Более надёжное хранение результатов.** Рассмотреть применение SQLite вместо обычного словаря для сохранения состояния между запусками программы. Обеспечить повторяемость регистрации инцидента и после перезапуска приложения.
