# Практическое задание №3. Разработка многоуровневой системы защиты автономного ИИ-агента

**Модуль 3. Shield Pipeline и Guardrails**

## Цель

Разработать и интегрировать в архитектуру автономного ИИ-агента многоуровневую систему безопасности **Shield Pipeline**, обеспечивающую проверку действий и данных перед их использованием.

Реализовать четыре уровня защиты: политики безопасности, эвристические проверки, оценку риска с помощью LLM-судьи и подтверждение человеком (Human-in-the-Loop, HITL).

В ходе выполнения необходимо освоить методы фильтрации входных и выходных данных, ограничения области допустимых действий (Guardrails), контроля ресурсов агента и автоматического запрета высокорисковых операций при истечении времени согласования (Timeout-to-Deny).

## Задание (шаги)

### Шаг 1. Подготовка проекта и архитектуры Shield Pipeline

Продолжить разработку системы обработки ИТ-инцидентов из практических заданий №1 и №2.

Создать каталог `assignments/03/` и реализовать дополнительный компонент `ShieldPipeline`, отвечающий за проверку предложений автономного агента.

Система должна последовательно использовать четыре уровня защиты:

| Уровень | Компонент         | Назначение                                                            |
| ------- | ----------------- | --------------------------------------------------------------------- |
| 1       | Policy Check      | Проверка соответствия действия установленным политикам                |
| 2       | Heuristic Check   | Обнаружение подозрительных ситуаций по заранее определённым признакам |
| 3       | LLM Judge         | Дополнительная оценка неоднозначных ситуаций                          |
| 4       | Human-in-the-Loop | Передача решения человеку при необходимости                           |

Предусмотреть следующие требования:

- Каждый уровень должен иметь собственную функцию проверки.
- Результаты проверок необходимо сохранять в истории прогона.
- Если действие запрещено политикой, последующие проверки не должны отменять этот запрет.
- Обращение к LLM-судье должно выполняться только при наличии соответствующих признаков риска.
- Решение LLM-судьи не должно самостоятельно разрешать регистрацию инцидентов.
- Операции, требующие ручного согласования, не должны выполняться до получения подтверждения.

Реализовать управляющую функцию `run_shield_pipeline()`, принимающую текущие наблюдения, предложенное действие и контекст выполнения.

Результат работы должен содержать итоговое решение, пройденные уровни защиты и причины обнаруженных ограничений.

### Шаг 2. Реализация первого уровня — Policy Check

Создать функцию `check_policy()`, проверяющую соответствие предложенного действия установленным политикам безопасности.

Использовать ограничения из предыдущей практической работы:

- Агент может читать данные мониторинга, журнал развёртываний и опубликованные регламенты.
- Доступ разрешён только к ресурсу `order-notifications` для обращений `REQ-1842` и `REQ-1843`.
- Повторная отправка уведомлений не входит в полномочия агента.
- Регистрация инцидента требует отдельного согласования дежурным оператором.

Подготовить тестовые запросы:

1. Получение состояния очереди уведомлений.
2. Чтение журнала развёртываний.
3. Попытка получить данные сервиса `payments`.
4. Попытка выполнить `resend_notifications`.

Для каждого запроса определить, разрешён ли он установленными политиками.

При нарушении правил вернуть соответствующий код отказа, например `not_allowed` или `resource_forbidden`.

Запрещённый инструмент должен блокироваться до фактического вызова.

### Шаг 3. Реализация второго уровня — Heuristic Check

Создать функцию `check_heuristics()`, обнаруживающую потенциально опасные ситуации на основании характеристик наблюдений.

В учебном проекте агент анализирует обращения о задержках уведомлений интернет-магазина.

Для обращения `REQ-1842` подготовить два варианта мониторинга:

**Сценарий А. Актуальные наблюдения**

- За 10 минут поступило 18 жалоб.
- Возраст старейшего сообщения в очереди — 17 минут.
- Снимок мониторинга получен менее 5 минут назад.

**Сценарий Б. Устаревшие наблюдения**

- За 10 минут поступило 18 жалоб.
- Возраст старейшего сообщения на момент снимка — 17 минут.
- Снимок мониторинга получен 22 минуты назад.

Реализовать следующие эвристические правила:

1. Если возраст снимка превышает 5 минут, отметить наблюдения как устаревшие.
2. Если одновременно зарегистрировано не менее 5 свежих жалоб, отметить необходимость дополнительной оценки.
3. При сочетании двух условий направить ситуацию на уровень LLM Judge.
4. Для актуального снимка продолжить штатную диагностику без вызова LLM-судьи.

Важно различать возраст самого снимка мониторинга и возраст старейшего сообщения в очереди. Эти значения характеризуют разные свойства системы.

Результат эвристической проверки должен содержать обнаруженные признаки риска и решение о необходимости дополнительной проверки.

### Шаг 4. Реализация третьего уровня — LLM Judge

Создать компонент `LLMJudge`, оценивающий ситуации, в которых обычные эвристики обнаружили неоднозначность.

Судья должен принимать только три числовых параметра:

- `complaints_count` — количество свежих жалоб;
- `snapshot_age_minutes` — возраст снимка мониторинга;
- `oldest_message_age_minutes` — возраст старейшего сообщения на момент снимка.

На основе этих данных судья формирует структурированное заключение.

Предусмотреть следующие варианты оценки:

| Оценка                  | Значение                                  |
| ----------------------- | ----------------------------------------- |
| `low_risk`              | Данные не указывают на высокий риск       |
| `likely_incident`       | Имеются признаки значимого инцидента      |
| `insufficient_evidence` | Данных недостаточно для уверенного вывода |

Результат должен содержать код оценки и текстовое объяснение.

Для выполнения задания допускается создать локальную имитацию LLM-судьи, возвращающую заранее определённые структурированные ответы. Подключение реальной языковой модели необязательно.

Реализовать проверку структуры ответа судьи.

Предусмотреть обработку следующих ситуаций:

- Судья возвращает корректное заключение.
- Судья возвращает неизвестную оценку.
- Судья возвращает ответ без обязательных полей.
- Источник решений недоступен.
- Ожидание ответа превышает установленный таймаут.

При ошибке необходимо сохранить `judge_unavailable` или соответствующий код ошибки и передать обращение на ручной разбор.

**Важно:** LLM-судья не должен иметь доступа к исполнительным инструментам и не должен изменять состояние инцидентов.

### Шаг 5. Реализация четвёртого уровня — Human-in-the-Loop

Создать механизм передачи неоднозначных ситуаций дежурному оператору.

Если эвристическая проверка обнаружила устаревший снимок при наличии продолжающихся жалоб, агент должен перейти в состояние `needs_review`.

Это условие обязательно даже в случае, если LLM-судья вернул оценку `low_risk`.

Реализовать следующие возможности:

1. Сохранение результатов всех выполненных проверок.
2. Формирование причины передачи обращения на ручной разбор.
3. Отображение оператору собранных наблюдений и заключения судьи.
4. Фиксация факта принятия обращения на ручной разбор.
5. Запрет автоматической регистрации инцидента по неоднозначным данным.

Предусмотреть отдельный сценарий штатной диагностики, в котором агент собрал актуальные наблюдения и подготовил рекомендацию P2.

Для этого случая должна сохраняться процедура согласования регистрации, разработанная в практическом задании №2.

Необходимо различать два действия оператора: принятие обращения на ручной разбор и подтверждение регистрации инцидента. Первое не должно автоматически выполнять второе.

### Шаг 6. Реализация фильтрации входных данных

Создать функцию `filter_input()`, выполняющую проверку и очистку данных перед передачей автономному агенту.

Подготовить учебную выгрузку службы поддержки для обращения `REQ-1842`.

Выгрузка должна содержать:

- идентификатор обращения;
- текстовое описание проблемы;
- отдельное поле контакта покупателя;
- сведения о количестве обращений;
- время получения информации.

В текст описания добавить вымышленный адрес электронной почты `buyer-1842@example.invalid`.

Реализовать следующие проверки:

1. Допустимость набора входных полей.
2. Соответствие значений ожидаемым типам.
3. Ограничение длины описания до 1600 символов.
4. Проверка формата отдельного поля электронной почты.
5. Отклонение недопустимых управляющих символов.
6. Маскирование адресов электронной почты, обнаруженных внутри текста.

Количество жалоб и другие доверенные показатели мониторинга должны поступать из данных учебного стенда, а не подменяться значениями произвольной выгрузки поддержки.

Если входные данные имеют некорректную структуру, возвращать `invalid_run_input`.

Исходные конфиденциальные значения не должны включаться в сообщения об ошибках или журнал выполнения.

После фильтрации в истории агента должно сохраняться только очищенное описание.

### Шаг 7. Реализация фильтрации выходных данных

Создать функцию `filter_output()`, проверяющую решения, возвращаемые языковой моделью или её имитацией.

Допустимый ответ модели должен содержать только:

- `action` — код предлагаемого действия;

Дополнительно реализовать удаление распознаваемых адресов электронной почты и недопустимых управляющих символов из отображаемых текстовых объяснений.

При обнаружении некорректного ответа модели агент должен остановить выполнение следующего инструмента и перевести обращение на ручной разбор.

### Шаг 8. Реализация Guardrails для контроля инструментов

Расширить Executor системой ограничений для диагностических операций.

**Ограничение 1. Область доступа**

Разрешить диагностическое чтение только для `order-notifications` и только через четыре инструмента, определённые в модуле 2.

**Ограничение 2. Количество вызовов**

Установить максимальный бюджет — четыре чтения на один прогон.

Каждый инструмент допускается вызвать не более одного раза в рамках одного прогона.

Повторное чтение должно блокироваться с кодом `action_limit_reached`.

**Ограничение 3. Размер ответа**

Ограничить размер сериализованного JSON-ответа каждого инструмента до 2048 байт в кодировке UTF-8.

При превышении ограничения вернуть `response_too_large` без содержимого источника.

**Ограничение 4. Учёт неудачных вызовов**

Ошибки источника и таймауты также должны расходовать бюджет вызовов.

Нельзя предоставлять агенту дополнительную попытку только потому, что предыдущий вызов завершился ошибкой.

**Ограничение 5. Состояние прогона**

После завершения или закрытия диагностического прогона запретить новые чтения в рамках того же идентификатора.

Реализовать отдельный учёт бюджета для каждой комбинации прогона, обращения и вызывающего пользователя.

При использовании SQLite резервирование вызова должно выполняться атомарно до обращения к источнику. Для незавершённых прогонов предусмотреть удаление устаревших резервирований после одного часа.

Проверить, что параллельные запросы не могут превысить установленный лимит.

### Шаг 9. Реализация Timeout-to-Deny

Создать механизм автоматического запрета высокорисковых операций при истечении срока согласования.

Для регистрации инцидента установить стандартное время подтверждения — 10 минут с момента сохранения черновика.

Значение должно настраиваться с помощью параметра `APPROVAL_TIMEOUT_SECONDS`.

При сохранении черновика необходимо зафиксировать:

- идентификатор прогона;
- параметры предлагаемого инцидента;
- время создания;
- крайний срок согласования;
- текущий статус.

Реализовать функцию `check_approval_timeout()`, которая определяет допустимость подтверждения по серверному времени.

Подготовить два сценария.

| Параметр              | Сценарий А                                               | Сценарий Б         |
| --------------------- | -------------------------------------------------------- | ------------------ |
| Создание черновика    | 14:12                                                    | 14:12              |
| Истечение срока       | 14:22                                                    | 14:22              |
| Попытка подтверждения | 14:19                                                    | 14:23              |
| Результат             | Регистрация разрешена при прохождении остальных проверок | `approval_expired` |

При истечении срока:

1. Перевести черновик в состояние `approval_expired`.
2. Запретить регистрацию инцидента.
3. Вернуть код `approval_expired`.
4. Сохранить причину отказа в журнале.
5. Предусмотреть возможность нового диагностического прогона с новым сроком согласования.

Если используется HTTP API, отказ при попытке подтвердить просроченный черновик должен возвращать статус `409`.

Проверять срок необходимо не только при получении запроса, но и непосредственно перед записью инцидента внутри транзакции.

Повторное обращение к уже успешно выполненной регистрации должно возвращать сохранённый идентификатор, не создавая дубликат.


Проверки лучше реализовать как отдельные функции, возвращающие структурированные результаты.

Это позволит изменять пороговые значения без переписывания всего Shield Pipeline.

### 4. Проверка ответа LLM-судьи

Использовать строго ограниченный перечень допустимых оценок:

```python
ALLOWED_VERDICTS = {
    "low_risk",
    "likely_incident",
    "insufficient_evidence",
}
```

Проверять не только значение оценки, но и структуру всего ответа.

Некорректный ответ не должен автоматически интерпретироваться как `low_risk`.

### 5. Учёт вызовов инструментов

Не рекомендуется увеличивать счётчик только после успешного получения результата.

Резервирование вызова должно происходить до выполнения операции, иначе при ошибках и параллельных запросах возможно превышение лимита.

Для проверки размера ответа использовать фактический размер сериализованных данных в байтах, а не количество символов строки.

### 6. Контроль времени

Для хранения срока согласования использовать `datetime` с явно заданным часовым поясом.

Срок должен рассчитываться на стороне исполнителя, а не приниматься из ответа агента или браузера.

При проверке граничных условий считать срок истёкшим, если текущее время больше либо равно установленному моменту завершения согласования.

### 7. Журналирование Shield Pipeline

Для каждого выполненного уровня рекомендуется сохранять:

- идентификатор прогона;
- название уровня проверки;
- результат;
- код отказа или обнаруженного риска;
- краткое объяснение;
- время выполнения.

В журнал не должны попадать исходные контакты покупателей, секреты доступа или другие сведения, удалённые входными фильтрами.

## Советы по улучшению работы

**1. Конфигурируемость правил.** Вынести пороговые значения эвристик, лимиты инструментов и сроки согласования в отдельный конфигурационный файл. Это позволит изменять параметры безопасности без модификации основной логики.

**2. Независимое тестирование уровней.** Проверять каждый компонент Shield Pipeline отдельно, а затем проводить интеграционные тесты всей последовательности. Такой подход упрощает выявление причин отказа.

**3. Разделение оценок и разрешений.** Не использовать результат LLM-судьи как окончательное разрешение на выполнение операции. Модель может помогать оценивать риск, но проверка полномочий и обязательных условий должна оставаться детерминированной.

**4. Защита от обхода ограничений.** Проверить возможность повторного вызова инструментов через другие имена, новые запросы с прежним идентификатором прогона и параллельное выполнение. Ограничения должны применяться в самом Executor.

**5. Надёжное хранение состояния.** Для бюджета вызовов и сроков согласования использовать SQLite с транзакциями. Это позволит сохранять ограничения между перезапусками приложения.

**6. Наблюдаемость.** Добавить возможность просмотра истории проверок, чтобы определить, на каком уровне Shield Pipeline было принято решение об остановке и какие данные послужили основанием.
