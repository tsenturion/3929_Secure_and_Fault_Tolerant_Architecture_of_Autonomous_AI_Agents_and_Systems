# Практическое задание №2. Разработка архитектуры безопасности автономного ИИ-агента

**Модуль 2. Архитектурные принципы безопасности**

## Цель

Разработать систему управления действиями автономного ИИ-агента, в которой принятие решений и выполнение операций разделены между независимыми программными компонентами.

Реализовать принципы **разделения когнитивных и исполнительных функций, Fail-Closed, Zero Trust, иерархии приоритетов безопасности и детерминированной проверки инструментов**.

В ходе выполнения необходимо научиться проектировать архитектуру, в которой агент может самостоятельно предлагать решения, но не может обходить ограничения безопасности, получать неразрешённый доступ к данным или выполнять критические операции без подтверждения полномочий.

## Задание (шаги)

### Шаг 1. Подготовка проекта и разделение компонентов

Продолжить разработку агента для обработки ИТ-обращений интернет-магазина из практического задания №1.

Создать каталог `assignments/02/` и реализовать два основных компонента:

**Agent (когнитивный компонент)** — отвечает за анализ информации, выбор инструментов и формирование рекомендаций.

**Executor (исполнительный компонент)** — принимает запросы агента, независимо проверяет их допустимость и выполняет только разрешённые операции.

Предусмотреть следующие ограничения:

- Агент не должен непосредственно изменять хранилище инцидентов.
- Агент не должен самостоятельно назначать себе полномочия.
- Все обращения к диагностическим инструментам должны проходить через Executor.
- Executor должен иметь собственные правила проверки, не зависящие от рекомендаций агента.
- Операции регистрации инцидентов должны выполняться отдельно от диагностических действий.

На первом этапе допускается взаимодействие компонентов через вызовы Python-функций, однако проверки безопасности должны находиться на стороне Executor.

### Шаг 2. Реализация независимого исполнителя

Создать класс `Executor`, принимающий запросы на выполнение инструментов.

Для диагностического агента предусмотреть четыре разрешённых инструмента:

| Инструмент                | Назначение                               |
| ------------------------- | ---------------------------------------- |
| `get_service_status`      | Чтение состояния сервиса                 |
| `get_deployment_log`      | Чтение журнала развёртываний             |
| `find_incident_runbook`   | Поиск регламента массовой задержки       |
| `find_individual_runbook` | Поиск регламента индивидуальной доставки |

Каждый запрос должен содержать идентификатор обращения, идентификатор прогона, код инструмента и целевой ресурс. Данные аутентификации должны передаваться отдельно от результата работы модели.

Реализовать проверку запрашиваемого действия по реестру инструментов.

Если агент предлагает выполнить `resend_notifications`, `delete_incident` или другое отсутствующее в реестре действие, Executor должен вернуть отказ `not_allowed`.

При успешной проверке исполнитель вызывает соответствующую функцию и возвращает результат.

**Важно:** запрещённые инструменты не должны вызываться даже в том случае, если агент указывает, что действие необходимо для устранения критической проблемы.

### Шаг 3. Реализация принципа Fail-Closed

Добавить механизм, при котором отсутствие необходимых сведений для проверки безопасности приводит к запрету операции, а не к автоматическому разрешению.

Использовать файл `config/on-call.json`, содержащий сведения о назначении дежурного оператора.

Пример структуры:

```json
{
  "assignments": {
    "Уведомления": "duty_operator"
  }
}
```

Реализовать функцию `check_assignment()`, проверяющую, имеет ли пользователь право подтвердить регистрацию инцидента в указанной очереди.

Предусмотреть следующие ситуации:

1. Файл существует, содержит корректные данные и оператор назначен на очередь — проверка успешна.
2. В расписании отсутствует назначение — операция отклоняется с кодом `assignment_missing`.
3. На очередь назначен другой оператор — возвращается `not_assigned`.
4. Файл отсутствует, недоступен или содержит некорректную структуру — возвращается `policy_unavailable`.

При отказе регистрация должна блокироваться, а черновик оставаться в состоянии `awaiting_approval`.

После восстановления корректного расписания необходимо обеспечить возможность повторного подтверждения этого же черновика.

Не допускается использование автоматического разрешения в качестве резервного поведения при ошибке чтения конфигурации.

### Шаг 4. Реализация принципа Zero Trust

Создать систему проверки доступа, в которой каждый запрос рассматривается как потенциально недоверенный независимо от того, из какого компонента он поступил.

Предусмотреть три типа участников:

- `diagnostic-agent` — сервис, выполняющий диагностику;
- `duty_operator` — дежурный оператор;
- `observer` — пользователь с правами просмотра.

Реализовать проверку сервисного ключа и пользовательского ключа на стороне Executor.

Правила доступа:

| Участник         | Чтение разрешённых данных                                     | Подтверждение регистрации            |
| ---------------- | ------------------------------------------------------------- | ------------------------------------ |
| diagnostic-agent | Разрешено при корректной аутентификации и авторизации запроса | Запрещено                            |
| duty_operator    | Разрешено в пределах полномочий                               | Разрешено при действующем назначении |
| observer         | Разрешён просмотр доступных результатов                       | Запрещено                            |

Дополнительно реализовать ограничения ресурсов:

- Диагностический агент может читать данные `order-notifications` для обращений `REQ-1842` и `REQ-1843`.
- Запрос данных ресурса `payments` должен отклоняться с кодом `resource_forbidden`.
- Попытка подтверждения регистрации от пользователя `observer` должна отклоняться с кодом `operation_forbidden`.
- Запрос с отсутствующим или неверным сервисным ключом должен отклоняться до выполнения инструмента.

Проверка доступа должна выполняться при каждом новом запросе. Результаты предыдущей успешной проверки не должны автоматически разрешать последующие действия.

### Шаг 5. Реализация иерархии приоритетов безопасности

Создать механизм принятия решений, основанный на учебной аналогии с иерархией законов Азимова.

Реализовать три уровня приоритета:

**Уровень 1. Защита данных — высший приоритет**

Запретить публикацию в общем трекере структурированных полей, содержащих контакты покупателей и другие сведения, не предназначенные для публикации.

Если черновик содержит поле `customer_email` или `customer_contacts`, операция должна быть отклонена с кодом `data_policy_denied`.

**Уровень 2. Подтверждение и полномочия**

Если данные допустимы для публикации, проверить явное подтверждение оператора, его роль и актуальное назначение на очередь.

Отсутствие хотя бы одного обязательного условия должно блокировать регистрацию.

**Уровень 3. Рекомендация агента**

Если предыдущие уровни проверок пройдены, разрешить использование рекомендации агента о приоритете и очереди назначения, но только после проверки их соответствия правилам системы.

Реализовать функцию `check_priority_hierarchy()`, проверяющую все три уровня в установленном порядке.

Подготовить два черновика по обращению `REQ-1842`:

- Черновик с приоритетом P2, очередью «Уведомления» и полем `customer_contacts`.
- Черновик с тем же приоритетом и очередью, но содержащий только сводные показатели мониторинга и количество обращений.

Оба черновика должны получить подтверждение учебного дежурного оператора.

Первый вариант должен быть отклонён из-за нарушения политики данных. Второй должен успешно пройти проверки при наличии обязательных наблюдений и корректного назначения оператора.

**Важно:** правила более низкого уровня не могут отменять запреты более высокого уровня. Даже подтверждение дежурного не позволяет обойти политику защиты данных.

### Шаг 6. Детерминированные проверки перед выполнением инструментов

Разработать единый механизм проверки запросов `validate_action()`.

Перед вызовом диагностического инструмента необходимо проверить:

1. Корректность структуры запроса и обязательных параметров.
2. Подлинность вызывающего сервиса и пользователя.
3. Допустимость обращения для данного участника.
4. Разрешённость запрашиваемого ресурса.
5. Наличие инструмента в реестре разрешённых операций.

Для регистрации инцидента создать отдельную функцию `validate_registration()`.

Она должна дополнительно проверять:

- существование сохранённого черновика;
- состояние `awaiting_approval`;
- наличие явного подтверждения;
- допустимость публикуемых полей;
- соответствие приоритета и очереди исходному обращению;
- наличие обязательных наблюдений из мониторинга, журнала развёртываний и опубликованного регламента;
- роль оператора и его назначение на очередь.

Например, для `REQ-1842` отсутствие снимка очереди или опубликованного регламента должно приводить к отказу `evidence_required`.

Если очередь назначения изменена с «Уведомления» на «Платежи», регистрация должна отклоняться с кодом `invalid_draft`.

Все проверки должны возвращать предсказуемые результаты. Повторная проверка одного и того же запроса при неизменном состоянии системы должна давать одинаковое решение.

### Шаг 7. Реализация безопасной регистрации инцидентов

Создать отдельный метод `register_incident()`.

Он должен принимать идентификатор сохранённого прогона и подтверждение дежурного оператора, полученное через проверенный механизм аутентификации.

Необходимо обеспечить следующую последовательность:

1. Найти сохранённый черновик.
2. Проверить полномочия пользователя.
3. Проверить состояние и содержимое черновика.
4. Проверить актуальное расписание дежурств.
5. Проверить наличие обязательных доказательств.
6. Применить иерархию приоритетов безопасности.
7. При успешном прохождении всех проверок зарегистрировать инцидент.
8. Сохранить результат и вернуть идентификатор созданной записи.

Агент не должен иметь возможности передавать собственную команду регистрации в обход этой последовательности.

Реализовать защиту от повторного создания инцидента: повторное подтверждение успешно зарегистрированного прогона должно возвращать существующий идентификатор.

При использовании постоянного хранилища проверка отсутствия дубликата и запись инцидента должны выполняться атомарно.

### Шаг 8. Тестирование архитектуры безопасности

Создать автоматические тесты с использованием `pytest`.

Проверить следующие сценарии:

| №   | Сценарий                                        | Ожидаемый результат                |
| --- | ----------------------------------------------- | ---------------------------------- |
| 1   | Запрос разрешённого инструмента                 | `allowed`                          |
| 2   | Вызов неизвестного инструмента                  | `not_allowed`                      |
| 3   | Чтение ресурса `payments`                       | `resource_forbidden`               |
| 4   | Неверный сервисный ключ                         | Отказ до обращения к источнику     |
| 5   | Попытка регистрации от `observer`               | `operation_forbidden`              |
| 6   | Отсутствует назначение дежурного                | `assignment_missing`               |
| 7   | Файл расписания повреждён                       | `policy_unavailable`               |
| 8   | Черновик содержит контакты покупателей          | `data_policy_denied`               |
| 9   | Нет явного подтверждения                        | `confirmation_required`            |
| 10  | Отсутствуют обязательные наблюдения             | `evidence_required`                |
| 11  | Очередь заменена на «Платежи»                   | `invalid_draft`                    |

Дополнительно проверить, что при каждом отказе число записей в трекере не увеличивается и запрещённый инструмент фактически не вызывается.

## Подсказки по ключевым частям

Рекомендуемая структура проекта:

```text
    │   ├── test_priority.py
    │   └── test_validation.py
    └── README.md
```

Рекомендуется сохранить минимальную связанность компонентов. Агент должен обращаться к исполнителю через строго определённый программный интерфейс, а не напрямую к функциям изменения данных.

### 2. Реестр инструментов

Для сопоставления кодов инструментов с функциями удобно использовать словарь:

```python
TOOL_REGISTRY = {
    "get_service_status": get_service_status,
    "get_deployment_log": get_deployment_log,
    "find_incident_runbook": find_incident_runbook,
    "find_individual_runbook": find_individual_runbook,
}
```

Перед выбором функции из словаря необходимо проверить допустимость инструмента, ресурса и участника запроса.

Не следует использовать `eval()` или `exec()` для выполнения названий инструментов, полученных от агента.

### 3. Представление результатов проверки

Для результатов политики можно использовать словарь или класс со следующими полями:

```python
{
    "allowed": False,
    "code": "resource_forbidden",
    "reason": "Доступ к ресурсу запрещён"
}
```

Единый формат позволит независимо тестировать проверки и выводить понятные причины отказа.

### 4. Безопасная проверка полномочий

Не следует определять права только по строке `"role"`, переданной агентом или пользователем.

Сначала необходимо установить личность вызывающего участника по проверенному ключу, затем определить его полномочия из доверенной конфигурации.

Учебные секреты хранить в переменных окружения или локальном файле `.env`, исключённом из системы контроля версий. Не размещать реальные ключи в исходном коде и журналах.

### 5. Принцип Fail-Closed

При обработке ошибок полезно различать:

- отказ из-за нарушения правила безопасности;
- отказ из-за недоступности информации для проверки;
- временный сбой вызываемого инструмента.

Во всех трёх случаях запрещённое или неподтверждённое действие не должно выполняться.

При этом необходимо сохранять код и причину отказа, чтобы после устранения проблемы можно было корректно повторить запрос.

### 6. Проверка иерархии приоритетов

Порядок проверок должен быть явно определён в программе.

Необходимо учитывать, что разрешение одного уровня не означает автоматического разрешения всей операции.

Проверку структурированных полей не следует считать полноценной защитой от персональных данных внутри произвольного текста. Расширенная фильтрация свободного текста рассматривается отдельно.

### 7. Тестирование без реальных сервисов

Для проверки вызова инструментов можно использовать `unittest.mock`.

Это позволит установить, была ли фактически вызвана функция после проверки политики.

При тестировании использовать только учебные обращения, вымышленные контактные данные и локальные конфигурации.

## Советы по улучшению работы

**1. Независимость компонентов.** Реализовать взаимодействие агента и исполнителя через локальный HTTP API с использованием FastAPI. Это позволит физически разделить процессы и обеспечить проверку запросов на границе компонентов.

**2. Централизация политик безопасности.** Вынести правила доступа, проверки инструментов и ограничения публикации в отдельные модули. Это уменьшит дублирование кода и упростит изменение правил.

**3. Строгая типизация запросов.** Использовать `dataclass` или Pydantic для описания структуры запросов и результатов проверок. Это поможет отклонять некорректные данные до выполнения бизнес-логики.

**4. Журналирование решений.** Сохранять идентификатор прогона, действие, проверенный ресурс, результат и код отказа. Не записывать в журнал секреты аутентификации или запрещённые к публикации данные.

**5. Тестирование обходных путей.** Проверить не только штатное взаимодействие агента с исполнителем, но и прямое обращение к Executor с изменёнными параметрами, поддельной ролью пользователя или неизвестным инструментом.

**6. Защита от конкурентных запросов.** Рассмотреть ситуацию, когда два подтверждения поступают практически одновременно. Использовать транзакции и ограничения уникальности хранилища для предотвращения дублирования инцидентов.

## 5 вопросов для рефлексии (на подумать)

1. **Почему опасно объединять принятие решений и выполнение действий в одном компоненте автономного агента?** Каким образом независимый исполнитель уменьшает последствия ошибочного решения модели или успешной prompt injection атаки?

2. **Почему принцип Fail-Closed запрещает действие при недоступности системы проверки полномочий, даже если это может задержать устранение инцидента?** Какие риски возникают при использовании противоположного подхода Fail-Open?

3. **Почему в архитектуре Zero Trust недостаточно один раз проверить пользователя при входе в систему?** Как изменятся последствия компрометации агента, если каждое обращение к инструменту требует отдельной проверки ресурса и полномочий?

4. **Что должно произойти, если агент рекомендует опубликовать контакты покупателей, а дежурный оператор явно подтверждает это действие?** Почему в такой ситуации приоритет политики защиты данных должен быть выше рекомендации агента и подтверждения пользователя?

5. **Почему детерминированные проверки безопасности целесообразно выполнять программным кодом, а не поручать исключительно языковой модели?** Какие свойства таких проверок делают поведение системы более предсказуемым, воспроизводимым и пригодным для автоматического тестирования?

**Результат выполнения практического задания:** исходный код защищённой архитектуры автономного агента, независимый исполнитель инструментов, механизмы проверки доступа и согласования, автоматические тесты и файл `README.md`.

Разработанная система должна демонстрировать, что автономность агента не означает неограниченные полномочия. Агент отвечает за выбор действий и рекомендации, а возможность их фактического выполнения определяется независимыми, проверяемыми и предсказуемыми правилами безопасности.
