# Практическое задание №6. Разработка отказоустойчивой архитектуры автономных ИИ-агентов с прогнозированием перегрузок

**Модуль 6. Отказоустойчивость и Resilience**

## Цель

Разработать механизмы обеспечения отказоустойчивости автономной агентной системы, позволяющие сохранять корректность обработки обращений при сбоях отдельных компонентов, временной недоступности сервисов и повышенной нагрузке.

Реализовать принципы **Resilience**, включая восстановление распределённых операций, Graceful Degradation, паттерны Retry, Timeout и Circuit Breaker, мониторинг функционального здоровья сервисов и прогнозирование перегрузок с использованием рекуррентной нейронной сети LSTM.

В ходе выполнения необходимо научиться проектировать системы, способные обнаруживать сбои, сохранять промежуточные результаты, безопасно восстанавливать выполнение и заранее снижать нагрузку при прогнозируемой перегрузке.

## Задание (шаги)

### Шаг 1. Подготовка проекта и архитектуры отказоустойчивости

Продолжить разработку системы обработки ИТ-инцидентов интернет-магазина из предыдущих практических заданий.

Создать каталог `assignments/06/` и реализовать отдельную подсистему `ResilienceManager`, отвечающую за обработку отказов и восстановление работы компонентов.

Все сценарии должны выполняться на учебных данных без воздействия на реальные производственные системы.

### Шаг 2. Реализация устойчивого хранения состояния

Расширить систему хранения состояния с использованием PostgreSQL.

Настроить отдельный контейнер PostgreSQL, доступный исполнителю через внутреннюю сеть Docker Compose.

Реализовать хранение следующих сущностей:

- Обращения и диагностические прогоны.
- Наблюдения, собранные агентом.
- Черновики инцидентов.
- Подтверждения операторов.
- Transaction tokens и ключи идемпотентности.
- Зарегистрированные инциденты.
- Результаты выполненных операций.
- События аудита.

Состояние должно сохраняться при остановке и пересоздании контейнера исполнителя.

Исполнитель не должен хранить критически важные результаты исключительно в оперативной памяти.

Для регистрации инцидента обеспечить атомарное выполнение следующих изменений:

1. Создание записи в трекере.
2. Обновление состояния диагностического прогона.
3. Сохранение результата операции.
4. Фиксация события аудита.
5. Сохранение информации об использовании разрешения.

Все перечисленные изменения должны выполняться в одной транзакции PostgreSQL.

Если транзакция завершается ошибкой до фиксации, частично созданный инцидент не должен оставаться в хранилище.

### Шаг 3. Реализация восстановления после сбоя исполнителя

Создать механизм восстановления операций после аварийного завершения процесса Executor.

Подготовить два сценария.

**Сценарий А. Сбой до фиксации транзакции**

Исполнитель начинает регистрацию инцидента, но аварийно завершается до выполнения `COMMIT`.

После перезапуска необходимо:

- Проверить состояние базы данных.
- Убедиться, что незавершённые изменения откатились.
- Найти сохранённый черновик и согласование.
- Проверить, что разрешение ещё действительно.
- Повторить регистрацию с исходным идентификатором операции и ключом идемпотентности.

Ожидаемый результат: создан ровно один инцидент.

**Сценарий Б. Сбой после фиксации транзакции**

Исполнитель успешно завершает транзакцию, но останавливается до отправки ответа клиенту.

После перезапуска клиент повторяет исходный запрос.

Необходимо:

- Найти сохранённый результат операции.
- Повторно проверить право вызывающего участника на получение результата.
- Вернуть ранее созданный идентификатор инцидента.
- Не выполнять повторную запись.

Ожидаемый результат: в трекере остаётся один инцидент с прежним идентификатором.

Дополнительно предусмотреть ограничение уникальности по исходному обращению, чтобы параллельные прогоны не создавали несколько инцидентов для одного случая.

Для реализации допускается использовать транзакционные блокировки PostgreSQL.

**Важно:** после отката транзакции номера, выделенные последовательностью PostgreSQL, могут пропускаться. Это не должно считаться нарушением корректности системы.

### Шаг 4. Реализация Graceful Degradation

| `normal`      | Автономный агент выполняет диагностику                               |
| `degraded`    | Автоматическая диагностика ограничена, обращение передаётся человеку |
| `unavailable` | Выполнение невозможно, причина отказа сохраняется                    |

Подготовить сценарий, в котором агент уже получил данные мониторинга, но языковая модель перестала отвечать.

В сохранённом состоянии должны остаться:

- Идентификатор обращения.
- Идентификатор диагностического прогона.
- Последние успешные наблюдения.
- Сведения об очереди из 4 800 сообщений.

При этом система не должна удалять накопленные наблюдения или автоматически регистрировать инцидент.

### Шаг 5. Разработка резервного ручного маршрута

Реализовать возможность завершения диагностики без участия языковой модели.

Для обращения, переданного в ручную очередь, предусмотреть следующую последовательность:

1. Дежурный оператор открывает сохранённый прогон.
2. Система показывает ранее полученные наблюдения.
3. Оператор запускает повторную проверку доступных источников.
4. Исполнитель получает актуальные данные мониторинга.
5. Выполняется поиск журнала развёртываний.
6. Проверяется наличие опубликованного регламента `RB-NOTIFY-07`.
7. Оператор выбирает приоритет P2 и формирует черновик.
8. Регистрация выполняется после проверки полномочий и подтверждения.

Для регистрации использовать механизмы авторизации и transaction tokens из практического задания №4.

После успешного завершения обращения установить статус `completed_manually`.

В системе метрик такое завершение должно учитываться как успешное ручное закрытие, а не как полностью автономная обработка.

Если обязательный источник недоступен, обращение должно оставаться в ручной очереди до восстановления источника или получения необходимых доказательств допустимым способом.

### Шаг 6. Реализация паттерна Timeout

Создать механизм ограничения времени ожидания внешних сервисов.

Для чтения мониторинга установить следующие параметры:

| Параметр                        | Значение   |
| ------------------------------- | ---------- |
| Таймаут одной попытки           | 700 мс     |
| Общий бюджет запроса            | 1 700 мс   |
| Максимальное количество попыток | 2          |
| Задержка между попытками        | 120–180 мс |

Реализовать функцию `call_with_timeout()`, контролирующую продолжительность обращения к внешнему сервису.

Необходимо учитывать:

- Время самой операции.
- Время ожидания перед повтором.
- Общий оставшийся бюджет.
- Корректное прекращение ожидания после таймаута.

Если общий бюджет исчерпан, дополнительные попытки не допускаются.

Предусмотреть тестовый сервис, который отвечает с искусственной задержкой.

Проверить, что медленный источник не может блокировать работу агента на неопределённое время.

### Шаг 7. Реализация паттерна Retry

Разработать функцию `retry_request()`, выполняющую ограниченные повторы временно неудачных операций.

Повтор разрешается при:

- сетевой ошибке;
- таймауте;
- HTTP `502`;
- HTTP `503`;
- HTTP `504`.

Не выполнять автоматический повтор при:

- HTTP `400`;
- HTTP `401`;
- HTTP `403`;
- отказе политики безопасности;
- некорректных параметрах запроса.

Для задержки между попытками использовать случайное значение в диапазоне 120–180 мс (_jitter_).

Создать сценарий, при котором первая попытка чтения мониторинга возвращает HTTP `503`, а вторая завершается успешно.

Проверить, что результат второй попытки сохраняется в контексте агента.

В журнале должны отображаться обе физические попытки и их продолжительность.

При этом один логический вызов инструмента не должен обходить ограничения Guardrails за счёт внутренних повторов.

### Шаг 8. Реализация Circuit Breaker

Создать класс `CircuitBreaker`, предотвращающий постоянные обращения к неисправному сервису мониторинга.

Реализовать три состояния:

- `CLOSED` — запросы разрешены.
- `OPEN` — новые запросы блокируются.
- `HALF_OPEN` — разрешается один пробный запрос.

Установить следующие правила:

1. В состоянии `CLOSED` запросы выполняются в обычном режиме.
2. После двух логических чтений, исчерпавших все попытки из-за временных ошибок, Circuit Breaker переходит в `OPEN`.
3. В состоянии `OPEN` новые обращения к мониторингу блокируются на 5 секунд.
4. После истечения интервала разрешается один пробный запрос.
5. Если пробный запрос успешен, состояние меняется на `CLOSED`.
6. Если пробный запрос завершается временной ошибкой, состояние снова становится `OPEN`.

Circuit Breaker должен быть общим для обращений, использующих один и тот же сервис мониторинга.

Если запрос заблокирован открытым Circuit Breaker, обращение сохраняется с признаком отсутствия свежих метрик и передаётся на ручной разбор.

Подготовить отдельные тесты переходов между состояниями.

Проверить, что при одновременных обращениях в состоянии `HALF_OPEN` только один запрос становится пробным.

### Шаг 9. Безопасные повторы операций регистрации

Расширить механизм повторов для операций создания инцидентов.

В отличие от диагностических чтений, регистрация изменяет состояние системы и требует особого подхода.

Установить:

- Таймаут одной попытки — 2,5 секунды.
- Общий бюджет операции — 5,5 секунды.
- Обязательное использование transaction token.
- Обязательное использование `Idempotency-Key`.

При временной ошибке повторный запрос должен использовать те же параметры согласования и тот же ключ идемпотентности.

Если первоначальная операция уже была зафиксирована в PostgreSQL, повтор должен возвращать сохранённый результат.

Если политика безопасности отклонила регистрацию, повтор без изменения необходимых условий не должен выполняться.

Проверить, что ошибки связи не приводят к созданию нескольких инцидентов.

### Шаг 10. Реализация мониторинга функционального здоровья

Создать компонент `FunctionalHealthMonitor`, проверяющий не только доступность процессов, но и способность системы выполнять основные бизнес-операции.

Реализовать три HTTP-эндпоинта:

**1. Liveness**

`GET /api/health/live`

Проверяет, что процесс API работает и способен отвечать на запросы.

**2. Readiness**

`GET /api/health/ready`

Проверяет доступность исполнителя и возможность чтения хранилища прогонов.

При недоступности хранилища должен возвращаться HTTP `503`.

**3. Functional Health**

`GET /api/health/functional`

Выполняет синтетическую проверку основных зависимостей.

Предусмотреть проверку:

- Доступности хранилища.
- Свежести снимка мониторинга.
- Доступности каталога регламентов.
- Возможности найти опубликованный `RB-NOTIFY-07`.
- Доступности ручного маршрута.
- Состояния языковой модели по результатам её последних штатных вызовов.

Функциональная проверка не должна создавать инциденты, изменять историю рабочих прогонов или расходовать обычный бюджет диагностических инструментов.

Установить интервал автоматического обновления показателей — 15 секунд.

### Шаг 11. Проверка различий между Liveness, Readiness и Functional Health

Подготовить три сценария.

**Сценарий А. Полностью работоспособная система**

Все компоненты доступны, опубликованный регламент найден.

Ожидаемый результат: все основные проверки успешны.

**Сценарий Б. Каталог работает, но необходимый регламент отсутствует**

Подготовить копию индекса каталога, в которой отсутствует `RB-NOTIFY-07`.

Процесс каталога должен продолжать отвечать на запросы проверки живости.

При этом функциональная проверка поиска регламента должна завершаться ошибкой.

Ожидаемый результат:

- Liveness каталога — успешен.
- Readiness каталога — успешен.
- Поиск регламента — ошибка.
- Общий функциональный статус — `degraded`.
- Ручной маршрут остаётся доступен при работоспособных необходимых зависимостях.

**Сценарий В. Хранилище недоступно**

Смоделировать отказ подключения к PostgreSQL.

Ожидаемый результат:

- API отвечает на Liveness.
- Readiness возвращает HTTP `503`.
- Функциональная проверка фиксирует недоступность хранилища.
- Операции регистрации блокируются.

Дополнительно предусмотреть, что доступность языковой модели не определяется исключительно существованием её конфигурации.

До первого успешного штатного обращения состояние модели может быть обозначено как `model_unverified`.

Не выполнять платные запросы к модели только ради фоновой проверки её работоспособности.

### Шаг 12. Подготовка данных для прогнозирования перегрузки

Создать модуль `forecasting`, использующий исторические временные ряды нагрузки на очередь ИТ-обращений.

Подготовить синтетический набор данных за 48 дней с минутным шагом.

Каждая запись должна содержать:

- `timestamp` — время измерения;
- `queue_length` — длину очереди;
- `arrivals_count` — количество поступивших обращений;
- `estimated_wait_minutes` — оценку времени ожидания.

Предусмотреть обычные периоды нагрузки, вечерние пики и отдельные эпизоды перегрузки.

Данные должны содержать последовательности, позволяющие наблюдать постепенное увеличение нагрузки перед достижением критического значения.

Разделить данные строго по времени:

| Выборка    | Период           | Назначение                            |
| ---------- | ---------------- | ------------------------------------- |
| Training   | Первые 32 дня    | Обучение модели                       |
| Validation | Следующие 8 дней | Настройка параметров и порога тревоги |
| Test       | Последние 8 дней | Итоговая оценка                       |

Не допускается случайное перемешивание временных интервалов между обучающей и тестовой выборками.

Параметры нормализации рассчитывать исключительно по обучающим данным.

### Шаг 13. Разработка и обучение LSTM

Создать модель прогнозирования перегрузки с использованием LSTM.

Модель должна получать последовательность наблюдений за последние 12 минут.

Для каждой минуты использовать три признака:

1. Длина очереди.
2. Количество новых обращений.
3. Оценка времени ожидания.

Размер входного окна — 12 временных шагов с тремя признаками на каждом шаге.

Задача модели — определить вероятность того, что в течение следующих 10 минут оценка ожидания достигнет или превысит 8 минут.

Для реализации рекомендуется использовать PyTorch с `torch.nn.LSTM`.

Допускается разработка модели на NumPy с самостоятельной реализацией необходимых операций.

Необходимо:

- Подготовить обучающие последовательности.
- Сформировать целевые значения.
- Создать архитектуру LSTM.
- Реализовать обучение.
- Сохранить веса модели.
- Реализовать загрузку весов.
- Создать функцию `predict_overload()`.

Результатом прогнозирования должна быть числовая оценка риска в диапазоне от 0 до 1.

Порог классификации подобрать на валидационной выборке.

### Шаг 14. Сравнение LSTM с пороговым методом

Разработать базовый метод обнаружения перегрузки без машинного обучения.

Пороговое правило должно формировать сигнал, когда текущее оценочное время ожидания достигает 8 минут.

Сравнить его с LSTM на одинаковой тестовой выборке.

Для оценки использовать следующие показатели:

- Количество обнаруженных эпизодов перегрузки.
- Количество пропущенных эпизодов.
- Количество ложных предупреждений.
- Среднее время предупреждения до начала перегрузки.

Считать одним эпизодом всплески перегрузки, разделённые интервалами не более 10 минут.

Для LSTM учитывать первый сигнал, поступивший в пределах десятиминутного горизонта до начала эпизода.

Предупреждение считать ложным, если в следующие 10 минут перегрузка не наступила.

Для оценки ложных предупреждений использовать только моменты, для которых доступен полный горизонт будущих наблюдений.

Оформить результаты в сравнительной таблице.

В изученном учебном примере оба метода обнаруживали шесть эпизодов, LSTM предупреждала в среднем за 7,3 минуты и формировала шесть ложных тревог, а пороговый метод реагировал при наступлении перегрузки.

Полученные при самостоятельном обучении результаты могут отличаться. Необходимо объяснить различия и оценить практическую полезность раннего предупреждения.

### Шаг 15. Проактивное управление нагрузкой на основе прогноза

Создать компонент `ProactiveLoadManager`, использующий результат LSTM для изменения интенсивности фоновых операций.

При высоком прогнозируемом риске система должна временно уменьшать нагрузку, создаваемую автоматическими функциональными проверками.

Реализовать следующую политику:

| Состояние                          | Частота фоновых проверок |
| ---------------------------------- | ------------------------ |
| Нормальная нагрузка                | Каждые 15 секунд         |
| Высокий прогнозируемый риск        | Каждые 60 секунд         |
| Восстановление нормальной нагрузки | Возврат к 15 секундам    |

Ограничение должно распространяться только на фоновые автоматические функциональные проверки.

Не допускается замедлять:

- Ручные проверки оператора.
- Приём новых обращений.
- Liveness и Readiness.
- Подтверждение согласованных операций.
- Регистрацию инцидентов.

При попытке выполнить отложенную автоматическую проверку возвращать HTTP `429` с заголовком `Retry-After`.

Предусмотреть ограничение продолжительности режима снижения фоновой нагрузки — не более 16 минут подряд.

После завершения этого периода система должна восстановить обычную частоту проверок, даже если риск остаётся повышенным. Повторное снижение нагрузки допускается по правилам нового интервала.

### Шаг 16. Моделирование вечернего пика нагрузки

Разработать симулятор, позволяющий сравнить работу системы с проактивным управлением и без него.

Подготовить два режима:

**Режим А. Обычная работа**

Фоновые проверки выполняются с постоянной периодичностью 15 секунд.

**Режим Б. Проактивное управление**

При прогнозируемой перегрузке периодичность фоновых проверок временно увеличивается до 60 секунд.

Для обоих режимов использовать одинаковые:

- 3 244 входящих обращения;
- временные метки поступления;
- вычислительные ресурсы;
- скорость обработки;
- начальные состояния очереди.

В модели учитывать, что каждый фоновый вызов потребляет часть общей вычислительной мощности. Для учебной симуляции установить стоимость одного фонового вызова в пять условных единиц мощности.

Рассчитать:

1. Количество выполненных фоновых проверок.
2. Среднее время ожидания до начала обработки.
3. 95-й процентиль времени ожидания.
4. Максимальную длину очереди.
5. Количество периодов ограничения фоновых операций.

Сравнить два режима и определить, уменьшает ли проактивное управление задержки обработки.

В рассмотренном учебном сценарии 95-й процентиль ожидания снижался с 20 до 15 минут, а число фоновых проверок — со 150 до 126.

При самостоятельной реализации необходимо получить собственные результаты и объяснить их зависимость от параметров симуляции и качества прогноза.

Состояние прогона должно сохраняться перед передачей обращения на ручной разбор.

Не следует заменять отсутствующие наблюдения вымышленными значениями или продолжать автоматическую регистрацию при недоступности обязательных данных.

```python
TOTAL_TIMEOUT = 1.7

RETRY_DELAY_MIN = 0.12
RETRY_DELAY_MAX = 0.18
```

При расчёте оставшегося времени учитывать задержку между попытками.

### 5. Реализация Circuit Breaker

Состояния удобно представить с использованием `Enum`:

```python
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"
```

Для хранения времени открытия использовать монотонные часы.

При параллельной работе необходимо обеспечить безопасное изменение состояния Circuit Breaker.

### 6. Проверка функционального здоровья

Разделять проверки живости процесса, готовности сервиса и реальной доступности бизнес-функций.

Успешный ответ `/health/live` не должен автоматически означать, что система способна зарегистрировать инцидент или найти необходимый регламент.

### 7. Подготовка данных для LSTM

Для формирования обучающей выборки использовать скользящее окно длиной 12 минут.

Каждая последовательность должна содержать три признака.

Целевое значение формировать на основании следующих 10 минут ряда, не включая будущие наблюдения в признаки текущего примера.

### 8. Обучение нейронной сети

Для реализации LSTM в PyTorch использовать `torch.nn.LSTM`.

Для задачи бинарной классификации можно применять выходной слой с одним логитом и функцию потерь `BCEWithLogitsLoss`.

При обучении контролировать значение функции потерь на валидационной выборке.

Не подбирать итоговый порог классификации на тестовых данных.

### 9. Оценка прогнозов

Необходимо различать обнаружение перегрузки в момент её наступления и предупреждение о перегрузке заранее.

Помимо количества верных прогнозов учитывать ложные тревоги и время упреждения.

Проверять прогноз на отдельных эпизодах перегрузки, а не только на отдельных минутах.

### 10. Безопасное проактивное управление

Результат LSTM должен влиять только на заранее разрешённые параметры фоновой нагрузки.

Нейронная сеть не должна самостоятельно изменять права доступа, правила регистрации или ограничения безопасности.

Рекомендуется отделить модель прогнозирования от компонента, применяющего управляющую политику.

## Советы по улучшению работы

**1. Разделение восстановления и бизнес-логики.** Не следует размещать обработку всех сбоев непосредственно в коде автономного агента. Выделение самостоятельных компонентов Retry, Circuit Breaker и Recovery упрощает тестирование и повторное использование механизмов.

**2. Ограничение количества повторов.** Даже временные ошибки не должны приводить к бесконечным запросам. Повторы увеличивают нагрузку на неисправный сервис и могут усугубить перегрузку.

**3. Безопасность повторной регистрации.** Для операций записи необходимо использовать идемпотентность и транзакции. Наличие Retry само по себе не обеспечивает защиту от дубликатов.

**4. Сохранение частичной работоспособности.** При сбое языковой модели целесообразно сохранять функции просмотра обращений, чтения доступных данных и ручного согласования. При этом нельзя обходить обязательные проверки безопасности.

**5. Раздельный мониторинг зависимостей.** Проверять не только доступность контейнеров, но и успешность выполнения конкретных функций. Работающий HTTP-сервер может возвращать ошибки при обращении к базе или каталогу.

**6. Контроль качества LSTM.** Сравнивать прогноз с простым пороговым методом. Более сложная нейронная сеть имеет практическую ценность только в том случае, если обеспечивает полезное раннее предупреждение при приемлемом количестве ложных тревог.

**7. Изоляция прогнозирования от критических операций.** Система прогнозирования должна изменять только разрешённые параметры фоновой нагрузки. Ошибка модели или неверный прогноз не должны блокировать подтверждение инцидентов и доступность ручного управления.
