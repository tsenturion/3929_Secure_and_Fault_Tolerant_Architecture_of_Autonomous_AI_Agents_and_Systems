# Практическое задание №7. Разработка защищённой мультиагентной системы с контролем информационных потоков и предотвращением утечек данных

**Модуль 7. Мультиагентная координация и защита данных**

## Цель

Разработать защищённую мультиагентную архитектуру, в которой несколько автономных агентов совместно выполняют задачи, обмениваются результатами и формируют согласованные решения без нарушения границ доступа и политик безопасности.

Реализовать **централизованную и децентрализованную координацию агентов, иерархическую архитектуру Master Agent, Information Flow Control (IFC), защиту от эксфильтрации данных и ограничение доступа к сетевым и файловым ресурсам**.

В ходе выполнения необходимо освоить механизмы безопасной передачи информации между агентами, проверки происхождения сообщений, разграничения полномочий, предотвращения утечек конфиденциальных сведений и защиты от Server-Side Request Forgery (SSRF).

## Задание (шаги)

### Шаг 1. Подготовка мультиагентной архитектуры

Продолжить разработку системы обработки ИТ-инцидентов интернет-магазина из предыдущих практических заданий.

Создать каталог `assignments/07/` и реализовать взаимодействие нескольких агентов.

Предусмотреть следующие компоненты:

| Компонент                   | Назначение                                         |
| --------------------------- | -------------------------------------------------- |
| `DiagnosticAgent`           | Анализ состояния сервисов и журналов развёртываний |
| `RunbookAgent`              | Поиск и проверка опубликованных регламентов        |
| `MasterAgent`               | Распределение заданий и объединение результатов    |
| `Coordinator`               | Централизованная координация агентов               |

| `InformationFlowController` | Контроль допустимости передачи данных              |

| `SourceAccessGuard`         | Проверка доступа к сетевым и файловым источникам   |

В качестве основного сценария использовать обращение `REQ-1842` о массовой задержке электронных уведомлений.

Исходные данные:

- В очереди находится 4 800 уведомлений.

Распределить задачи между агентами:

**DiagnosticAgent** должен получить данные мониторинга и журнал развёртываний.

**RunbookAgent** должен найти опубликованный регламент `RB-NOTIFY-07`.

**MasterAgent** должен проверить достаточность полученных доказательств и подготовить итоговую рекомендацию для дежурного оператора.

Использовать механизмы аутентификации, авторизации, журналирования и отказоустойчивости, реализованные в предыдущих модулях.

### Шаг 2. Реализация централизованной координации

Создать класс `CentralizedCoordinator`, управляющий взаимодействием агентов.

Предусмотреть следующий порядок работы:

1. Создать идентификатор общего прогона.
2. Сформировать задания для DiagnosticAgent и RunbookAgent.
3. Передать задания соответствующим агентам.
4. Получить результаты диагностики и поиска регламента.
5. Проверить принадлежность ответов текущему прогону.
6. Сохранить полученные наблюдения.
7. Объединить результаты в общий контекст.
8. Подготовить черновик рекомендации.

Все сообщения между агентами и координатором должны содержать:

- `message_id` — уникальный идентификатор сообщения;
- `run_id` — идентификатор прогона;
- `case_id` — идентификатор обращения;
- `sender` — идентичность отправителя;
- `receiver` — предполагаемый получатель;
- `message_type` — тип сообщения;
- `payload` — передаваемые данные.

Необходимо обеспечить защиту от повторной доставки сообщений.

Если координатор повторно получает сообщение с тем же идентификатором и неизменным содержимым, оно не должно повторно учитываться.

Если сообщение имеет прежний идентификатор, но изменённое содержимое, необходимо зафиксировать конфликт и отклонить повтор.

Для подготовки итоговой рекомендации координатор должен получить два различных подтверждённых результата: диагностику и опубликованный регламент.

До получения обязательных сведений регистрация инцидента не допускается.

### Шаг 3. Реализация децентрализованной координации

Разработать альтернативный режим взаимодействия без центрального координатора.

В этом режиме агенты должны обмениваться результатами напрямую.

Предусмотреть следующую последовательность:

1. DiagnosticAgent собирает информацию об очереди уведомлений.
2. DiagnosticAgent передаёт результаты RunbookAgent.
3. RunbookAgent проверяет сообщение и сохраняет полученные сведения.
4. RunbookAgent ищет опубликованный регламент.
5. RunbookAgent передаёт результаты DiagnosticAgent.
6. Оба агента независимо формируют итоговый контекст.
7. Система сравнивает результаты перед сохранением черновика.

Реализовать защиту от следующих ситуаций:

- Повторная доставка одинакового сообщения.
- Получение сообщения из другого прогона.
- Получение сообщения по другому обращению.
- Получение противоречивых данных.
- Отсутствие ответа одного из агентов.

В случае конфликта результатов черновик не должен автоматически сохраняться.

Если необходимый регламент отсутствует, сохранить полученные наблюдения и передать обращение на ручной разбор.

При реализации использовать одинаковое правило объединения результатов для обоих агентов.

### Шаг 4. Сравнение централизованной и децентрализованной координации

Создать функцию `compare_coordination_modes()`, запускающую два режима обработки одного обращения.

Для обоих режимов использовать одинаковые исходные данные и инструменты.

Смоделировать:

- Задержку доставки ответа RunbookAgent на 350 мс.
- Повторную отправку одного сообщения DiagnosticAgent.
- Успешное получение опубликованного регламента.
- Отсутствие регламента в отдельном тестовом прогоне.

Сравнить:

1. Количество переданных сообщений.
2. Время подготовки итоговой рекомендации.
3. Количество обработанных дубликатов.
4. Место хранения промежуточных результатов.
5. Поведение при недоступности одного агента.
6. Согласованность итоговых данных.

Для штатного обращения оба режима должны подготовить одинаковую рекомендацию P2.

После подтверждения дежурным оба прогона должны использовать общий механизм регистрации.

Проверить, что регистрация одного обращения через разные режимы координации не приводит к созданию нескольких инцидентов.

### Шаг 5. Разработка иерархии Master Agent и подчинённых агентов

Создать класс `MasterAgent`, отвечающий за управление подчинёнными агентами.

MasterAgent должен:

- Анализировать исходную задачу.
- Определять необходимые источники информации.
- Создавать задания для подчинённых агентов.
- Контролировать выполнение заданий.
- Проверять полученные результаты.
- Определять достаточность доказательств.
- Подготавливать итоговую рекомендацию.

Создать отдельную структуру задания `AgentTask`.

Каждое задание должно содержать:

- `task_id`;
- `run_id`;
- `case_id`;
- `agent_role`;
- `action`;
- `resource`;
- `deadline`.

Предусмотреть ограничения:

**DiagnosticAgent** может читать мониторинг и журнал развёртываний.

**RunbookAgent** может получать только опубликованные регламенты.

**MasterAgent** может распределять задания и объединять наблюдения, но не может самостоятельно регистрировать инциденты.

Исполнитель должен проверять допустимость задания для роли агента до вызова инструмента.

Нельзя предоставлять подчинённому агенту дополнительные полномочия только на основании того, что задание поступило от MasterAgent.

### Шаг 6. Обработка задержек и ошибок подчинённых агентов

Добавить механизм ожидания результатов подчинённых агентов.

Установить максимальное время ожидания обязательного ответа — 1,5 секунды.

Подготовить два сценария.

**Сценарий А. Штатная работа**

DiagnosticAgent получает данные мониторинга и журнал развёртываний.

После обнаружения массовой задержки MasterAgent поручает RunbookAgent найти регламент.

RunbookAgent возвращает опубликованный `RB-NOTIFY-07`.

MasterAgent подготавливает рекомендацию P2.

**Сценарий Б. Задержка ответа**

DiagnosticAgent успешно завершает диагностику.

RunbookAgent не успевает вернуть регламент за 1,5 секунды.

MasterAgent должен:

1. Сохранить результаты уже выполненной диагностики.
2. Зафиксировать незавершённое задание.
3. Указать причину остановки.
4. Не формировать окончательную рекомендацию P2 без регламента.
5. Передать обращение в состояние `needs_review`.

Проверить, что поздний ответ подчинённого агента не приводит к автоматической регистрации инцидента после завершения прогона.

### Шаг 7. Реализация Information Flow Control (IFC)

Создать компонент `InformationFlowController`, контролирующий перемещение информации между агентами и пользователями.

Для учебной системы предусмотреть два уровня классификации:

| Уровень                                         | Метка       | Содержание                                                            |
| ----------------------------------------------- | ----------- | --------------------------------------------------------------------- |
| Общедоступные для участников диагностики данные | `GENERAL`   | Размер очереди, возраст сообщений, канал уведомлений                  |
| Данные ограниченного доступа                    | `DUTY_ONLY` | Идентификаторы отдельных сообщений и служебные сведения для дежурного |

Каждое поле наблюдения должно иметь собственную метку доступа.

Например:

```python id="q6ut1h"
{
    "queue_length": {
        "value": 4800,
        "label": "GENERAL"
    },
    "oldest_message_age": {
        "value": 17,
        "label": "GENERAL"
    },
    "message_id": {
        "value": "MSG-1842-01",
        "label": "DUTY_ONLY"
    }
}
```

Реализовать функцию `check_information_flow()`, определяющую допустимость передачи конкретных полей от отправителя получателю.

Проверять:

1. Идентичность отправителя.
2. Идентичность получателя.
3. Метку конфиденциальности поля.
4. Допустимость передачи конкретного типа данных.
5. Наличие необходимого уровня доступа у получателя.

Если передача запрещена, поле не должно попадать в передаваемый контекст.

Результат проверки необходимо сохранять в журнале IFC без раскрытия содержимого запрещённого поля.

### Шаг 8. Реализация правил передачи информации между участниками

Создать таблицу разрешённых информационных потоков.

| Источник → Получатель              | Разрешённые сведения                                |
| ---------------------------------- | --------------------------------------------------- |
| DiagnosticAgent → RunbookAgent     | Размер очереди, возраст старейшего сообщения, канал |
| DiagnosticAgent → MasterAgent      | Разрешённые диагностические наблюдения              |
| MasterAgent → языковая модель      | Агрегированные сведения и разрешённый контекст      |
| Сохранённый прогон → duty_operator | Поля `GENERAL` и `DUTY_ONLY`                        |
| Сохранённый прогон → observer      | Только поля `GENERAL`                               |

Проверить следующие ситуации:

- RunbookAgent получает количество сообщений в очереди.
- RunbookAgent не получает идентификаторы отдельных сообщений.
- Дежурный оператор видит полную разрешённую ему карточку обращения.
- Наблюдатель получает сокращённое представление.
- Попытка передать поле `DUTY_ONLY` языковой модели блокируется.

Дополнительно реализовать сохранение меток при объединении результатов.

Если два источника передают одинаковое значение поля, но с разными метками, итоговое поле должно получить более строгую метку.

Если источники передают разные значения одного и того же поля, объединение должно завершаться ошибкой конфликта.

Нельзя автоматически снижать уровень конфиденциальности поля при передаче через промежуточного агента.

### Шаг 11. Контроль публикации данных и защищённый просмотр оригиналов

### Шаг 12. Реализация защиты от SSRF

Создать компонент `SourceAccessGuard`, проверяющий сетевые обращения агентов.

Запретить агентам самостоятельно определять произвольные адреса HTTP-запросов.

Разрешённые сетевые источники должны задаваться конфигурацией развёртывания.

Для учебного проекта предусмотреть:

- Сервис мониторинга `order-notifications`.
- Сервис каталога регламентов.
- Заранее определённые маршруты получения данных.

Реализовать проверку:

1. Идентичности вызывающего агента.
2. Разрешённости инструмента.
3. Допустимости запрошенного ресурса.
4. Соответствия идентификатора обращения области доступа.
5. Допустимости конкретного маршрута.

Использовать фиксированные схемы, хосты и порты, определённые конфигурацией.

Необходимо запретить построение адреса назначения из произвольного пользовательского URL.

Дополнительно отключить автоматическое следование HTTP-перенаправлениям и использование прокси из переменных окружения для защищённых внутренних клиентов.

### Шаг 13. Проверка защиты от SSRF

Подготовить набор учебных запросов.

| Запрос                                    | Ожидаемый результат    |
| ----------------------------------------- | ---------------------- |
| Получение состояния `order-notifications` | Разрешено              |
| Получение `RB-NOTIFY-07`                  | Разрешено              |

Все недопустимые адреса должны отклоняться до выполнения сетевого запроса.

Использовать моки сетевого транспорта, позволяющие проверить отсутствие фактического обращения к запрещённому адресу.

Дополнительно проверить, что URL, указанный внутри текста обращения, остаётся обычным текстом и не превращается автоматически в инструкцию для HTTP-клиента.

**Важно:** безопасность должна обеспечиваться разрешённым списком адресатов и маршрутов, а не только проверкой наличия подозрительных подстрок в URL.

### Шаг 14. Реализация ограничения доступа к файлам

Создать компонент `FileAccessGuard`, ограничивающий чтение файлов агентами.

Для учебного каталога регламентов определить разрешённый набор документов:

- `RB-NOTIFY-03`;
- `RB-NOTIFY-07`.

Файлы должны предоставляться через идентификатор опубликованного регламента, а не через произвольный путь, переданный агентом.

Реализовать функцию `read_allowed_document()`.

Перед чтением необходимо проверить:

1. Идентичность агента.
2. Разрешённость запрошенного документа.
3. Соответствие документа вызываемому инструменту.
4. Наличие опубликованной версии.
5. Отсутствие выхода за пределы разрешённого каталога.

Если документы загружаются из файловой системы, использовать заранее определённые имена файлов и доверенный каталог.

Запретить прямое чтение произвольных путей, символьных ссылок на запрещённые файлы и обращение за пределы разрешённого каталога.

Разрешённые документы подключать к контейнеру только для чтения.

### Шаг 15. Проверка файловых ограничений

Тестовые пути использовать только внутри собственного изолированного окружения.

### Шаг 16. Интеграция защитных механизмов в мультиагентный процесс

Объединить разработанные компоненты в единую систему.

При выполнении обращения `REQ-1842` обеспечить следующий порядок:

1. DiagnosticAgent получает задание.
2. Executor проверяет полномочия агента.
3. SourceAccessGuard проверяет допустимость источника.
4. DiagnosticAgent получает данные мониторинга.
5. InformationFlowController классифицирует поля наблюдений.
6. MasterAgent передаёт RunbookAgent разрешённые сведения.
7. RunbookAgent получает опубликованный регламент.
8. MasterAgent объединяет результаты.
9. DataProtectionGateway очищает данные для модели.
10. MasterAgent формирует рекомендацию P2.
11. Дежурный оператор подтверждает черновик.
12. Executor выполняет регистрацию с использованием transaction token.
13. Система аудита сохраняет события координации, проверки информационных потоков и публикации.

Проверить, что все действия объединены общим `trace_id`.

Запрещённые информационные потоки должны блокироваться независимо от способа координации агентов.

Допускается переиспользовать компоненты из предыдущих практических заданий.

### 2. Организация обмена сообщениями

Для описания структуры сообщений рекомендуется использовать Pydantic или `dataclass`.

Все сообщения должны проходить проверку структуры и идентичности отправителя.

Повторные сообщения необходимо сравнивать не только по идентификатору, но и по содержимому.

### 3. Координация асинхронных агентов

Для параллельного выполнения задач можно использовать `asyncio`.

При ожидании ответов предусмотреть общий срок выполнения.

Не следует ожидать ответа подчинённого агента бесконечно или формировать окончательное решение при отсутствии обязательных доказательств.

### 4. Разграничение полномочий подчинённых

Для каждого агента рекомендуется определить собственный набор разрешённых инструментов:

```python
AGENT_PERMISSIONS = {
    "diagnostic-agent": {
        "get_service_status",
        "get_deployment_log"
    },
    "runbook-agent": {
        "find_incident_runbook",
        "find_individual_runbook"
    }
}
```

Проверка должна выполняться исполнителем, а не только MasterAgent.

### 5. Классификация информации

Для уровней IFC удобно использовать `Enum`.

Рекомендуется рассматривать метку конфиденциальности как часть данных, которая должна сохраняться при передаче и объединении.

Преобразование данных не должно автоматически снижать уровень их защиты.

### 6. Фильтрация исходящих данных

Использовать принцип разрешённого списка полей.

Для обнаружения адресов электронной почты можно применять регулярные выражения, но следует учитывать ограничения такого подхода.

Проверку необходимо проводить непосредственно перед передачей данных за пределы защищённого компонента.

### 7. Предотвращение SSRF

Не создавать HTTP-клиент с адресом, непосредственно полученным из пользовательского текста или ответа модели.

Использовать фиксированные адреса доверенных сервисов и заранее определённые маршруты.

Для внутренних клиентов `httpx` можно отключить перенаправления и доверие к прокси из окружения.

### 8. Ограничение файлового доступа

Предпочтительно получать документы по разрешённым идентификаторам, а не по произвольным именам файлов.

Если используется файловая система, необходимо учитывать нормализацию путей и символьные ссылки.

Проверка безопасности должна производиться непосредственно перед чтением.

### 9. Проверка отсутствия утечек

Не ограничиваться поиском запрещённых значений только в ответе API.

Проверять:

- Контекст языковой модели.
- Сообщения между агентами.
- Публикуемые данные инцидента.
- Диагностические журналы.
- Сохранённые трассы.
- Ошибки HTTP API.

### 10. Интеграция с предыдущими модулями

Использовать ранее разработанные механизмы:

- Zero Trust для проверки полномочий.
- Shield Pipeline для проверки действий.
- Guardrails для ограничения инструментов.
- Transaction tokens для регистрации.
- Tamper-evident аудит для фиксации событий.
- Retry, Timeout и Circuit Breaker для обработки отказов.

## Советы по улучшению работы

**1. Минимизация связанности агентов.** Разделять ответственность между компонентами так, чтобы каждый агент выполнял ограниченный набор операций. Это упрощает сопровождение системы и уменьшает последствия компрометации отдельного агента.

**2. Защита протокола координации.** Проверять идентичность отправителя, принадлежность сообщения текущему прогону и корректность содержимого. Для распределённой системы важно учитывать повторную и несвоевременную доставку сообщений.

**3. Сохранение меток конфиденциальности.** Не удалять метки IFC после объединения результатов. Проверять допустимость передачи на каждой границе между участниками.

**4. Контроль данных перед отправкой.** Размещать механизмы предотвращения эксфильтрации на границе внешнего взаимодействия. Это помогает защищать данные даже при ошибках отдельных агентов.

**5. Изоляция сетевых источников.** Использовать фиксированные маршруты и разрешённые ресурсы вместо произвольных URL. Дополнительно ограничивать сетевую доступность контейнеров средствами Docker.

**6. Безопасная работа с файлами.** Предоставлять доступ к документам через контролируемый каталог или программный реестр. Не разрешать агентам самостоятельно выбирать абсолютные пути к файлам.

**7. Наблюдаемость мультиагентных процессов.** Связывать действия всех участников общим идентификатором трассы. Это позволит восстановить последовательность передачи сообщений, проверки полномочий и принятия решений.

## 5 вопросов для рефлексии (на подумать)

1. **В чём заключаются основные различия между централизованной и децентрализованной координацией автономных агентов?** Какой подход обеспечивает большую управляемость, а какой потенциально лучше переносит отказ отдельного координатора? Какие новые проблемы возникают при прямом обмене сообщениями между агентами?

2. **Почему MasterAgent не должен автоматически обладать всеми полномочиями подчинённых агентов?** Какие угрозы возникают, если управляющий агент может выполнять любые инструменты без независимой проверки исполнителем?

3. **Почему контроль информационных потоков нельзя заменить обычной проверкой прав доступа к API?** Каким образом конфиденциальные сведения могут попасть к неуполномоченному участнику через промежуточного агента, даже если исходный запрос был разрешён?

4. **Почему фильтрацию конфиденциальных данных необходимо выполнять непосредственно перед отправкой информации языковой модели или другому внешнему сервису?** Какие риски возникают, если проверять данные только при первоначальном получении обращения?

5. **Как злоумышленник может использовать возможность автономного агента обращаться к произвольным URL или читать файлы для получения доступа к внутренним ресурсам?** Почему разрешённый список источников и ограничение файловых путей обеспечивают более надёжную защиту, чем поиск отдельных запрещённых адресов и названий файлов?

**Результат выполнения практического задания:** исходный код защищённой мультиагентной системы, реализации централизованной и децентрализованной координации, иерархия Master Agent и подчинённых агентов, механизм IFC, система предотвращения эксфильтрации данных, защита от SSRF и несанкционированного файлового доступа, автоматические тесты и файл `README.md`.

**Ключевое требование:** передача задачи или информации между автономными агентами не должна приводить к расширению полномочий, снижению уровня защиты данных или обходу ограничений доступа. Каждый агент обязан действовать только в пределах разрешённых инструментов и информационных потоков, а любые внешние обращения должны проходить независимую проверку безопасности.
